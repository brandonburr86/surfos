# Brief: telnetd, a telnet server for SurfOS

Requested by the owner on 2026-10-06. SurfOS (branch `ai-dev`) runs surfsh on the
IdeaPad's four consoles and reaches the network through a USB Ethernet adapter. This
work lets another computer on the network telnet into the laptop and get a SurfOS shell.

## The owner's requests

| Request | How |
|---|---|
| Telnet from another computer on the network into the laptop and get the SurfOS shell | `telnetd` listens on TCP port 23; each connection gets its own surfsh (with the banner) on a pseudo-terminal |
| A basic telnet connection, nothing security-related | No login, no encryption. Anyone on the network who connects gets a shell with every kernel command (`fdisk`, `mkfs`, `reboot` included): the user guide says so, and to turn it off when not needed |
| Telnet to the laptop's IP address and land at a prompt | Port 23 on every interface; `telnetd on` prints the address to use |
| A program, `telnetd`, turned on and off, running in the background and accepting connections | `telnetd on [port]` starts the server (a detached background process), `telnetd off` stops it, `telnetd` (or `telnetd status`) says whether it runs and lists its sessions |

Decisions (the integrator's, stated to the owner): up to 4 sessions at once (a fifth
connection is told so and closed); `telnetd off` also ends the open sessions; connections
are logged to the kernel log (`dmesg`), not printed over the laptop's screen. macOS has
had no `telnet` since 10.13: `brew install telnet` on the Mac.

## Design

Programs have no network connections today (only kernel code uses TCP); a shell over a
connection needs a terminal that is not a screen, so that surfsh's raw mode, the pager,
`TTY_GETSIZE`, Ctrl+C and the kernel's commands (which print on their task's console)
work; and one process serving several connections needs `poll()`. So:

* **Network connections for programs** (`include/surfos/sock.h`): a listening socket or
  a connection is a file descriptor; `read`, `write`, `close`, `dup2`, `spawnfd` work on
  it. `tcp_listen`, `tcp_accept`, `tcp_connect`, `netinfo` in libsurf.
* **Pseudo-terminals** (`include/surfos/pty.h`): a `struct tty` with a *stream console*:
  `kputch()` on a pty's console appends the bytes to the master's output buffer instead
  of drawing cells (no UTF-8 decoding: the remote terminal does that; a kernel message's
  colour attribute becomes an ANSI SGR sequence). The pager counts the rows and columns
  `PTY_SETSIZE` gave and asks its question in the stream. Bytes the master writes go
  through the serial line's input rules. `TTY_CAPS` on a pty: UTF-8 and colour.
  Closing the last master descriptor hangs up: the tasks on the pty are killed (the kill
  that waits for the end of a system call); the pty is free once they are gone.
* **`poll()`** (`include/surfos/poll.h`): `vnode_ops->poll` says what a descriptor is
  ready for; whatever changes readiness calls `poll_wake()`, which wakes every task in
  `poll()` (one wait queue, `fs/poll.c`).
* **Processes** (`include/surfos/proc.h`): `procinfo()` lists the tasks (for `telnetd
  off` and `telnetd status`, and a `ps` program some day); `detach()` lets the server
  leave the shell that started it.
* **`/dev/kmsg`**: what a program writes there goes to the kernel log (`dmesg`).
* **telnetd** (one program):
  * `telnetd on [port]` looks for a running server (`procinfo`: a detached user task
    named `telnetd`); if none, it calls `tcp_listen(port)` itself, so "port in use" is
    reported at once, then starts the server with `spawnfd()`, handing it the listening
    descriptor, and prints `listening on <ip> port <port>` (or says to run `dhcp` when the
    interface has no address).
  * The server `detach()`es and loops on `poll()` over the listening descriptor and each
    session's connection and pty master. A new connection: `openpty()`, `PTY_SETSIZE`
    80x24, `spawnpty("/initrd/bin/surfsh", {"surfsh", "-l"}, master)`, the telnet
    negotiation (WILL ECHO, WILL SUPPRESS-GO-AHEAD, DO SUPPRESS-GO-AHEAD, DO NAWS).
  * From the connection to the pty: the telnet protocol is read (IAC commands and
    sub-negotiations; NAWS becomes `PTY_SETSIZE`; IAC IP and BRK become Ctrl+C; AYT is
    answered; CR LF and CR NUL become CR; IAC IAC is a 0xFF byte), the rest is written to
    the master. From the pty to the connection: LF becomes CR LF, a 0xFF byte IAC IAC.
  * A session ends when surfsh does (the master reads 0: the connection is closed) or
    when the client goes (the connection reads 0: the master is closed, which hangs up).
  * `telnetd off` finds the server and kills it; its descriptors close with it (the port
    is free, every client gets its FIN, every pty hangs up), so every session ends.
  * `telnetd` / `telnetd status`: running or not (pid), the sessions (pty, surfsh's pid).
  * The server logs to `/dev/kmsg`: listening, each session with the client's address,
    each end.
  * The telnet protocol is a pure module, tested on the host.

## Rules for every track

* Work only in your worktree and branch; another track's files are off limits, except
  where this brief names a shared file (the harnesses' `SMOKE` lists and scenarios: add
  your steps in one block of your own).
* Every commit builds and passes `make unittest` and `make test-all`; a change to the
  console, the terminal, the network, the USB path or `profile=laptop` also passes `make
  test-usb` at -O0 and -O2. Use `SURFOS_VOLUME=surfos-<track>` with `devenv/build.sh`.
* Kernel code follows the rules of `CLAUDE.md` (statuses, `curTask->con`, no shared
  statics, `shell_ask()`, giving up when a wait is cut short).
* Keep the 2004 file headers and style; new files get the same header block with the date.
* Small commits, one topic each, ending with the co-author line. Never push; never touch
  `master`, `04-source-recovered/` or `01-scans-original/`.

## After the reviews (2026-10-06)

Independent reviews of each track changed these points of the design above;
`docs/ARCHITECTURE.md` section 18 describes the result.

* A kernel thread started from a session (`tcpecho`, the self test's helpers) is put on
  F1, never on the pty, and outlives the session.
* A hangup's kill waits for the end of the call however long that takes; it never falls
  back to a kill at once after 2 seconds, which left a file system's lock held.
* A master's write never waits: it takes what fits in the input queue, and POLLOUT says
  a key fits. telnetd keeps a 1 KB buffer of keys per session, and a Ctrl+C drops the
  keys typed ahead and goes first; a line-mode Ctrl+C now drops type-ahead on the
  consoles too.
* TCP: `write()` takes what fits; a persist timer, keepalive and silly-window avoidance;
  no Nagle for programs' connections, which against real clients' delayed ACKs made
  typing lag.
* telnetd collects its shells promptly, and surfsh's prompt shows `≋@>` in a session. A
  session whose client has taken no output for 60 s while output waits is ended only when
  a new connection needs its place.
* A third review round: the server asks for BINARY (macOS's telnet strips the eighth bit
  of typed UTF-8 otherwise); a line-mode Ctrl+C ends an escape sequence in progress, so
  cursor keys that fill the queue cannot swallow it; the rest of a pasted block is skipped
  until the input pauses (`TTY_SKIP`), so no fragment of a pasted line runs as a command;
  and a paste into a program that reads arrives whole (telnetd reads the client only as
  fast as the master takes keys).
