# Brief: httpd, a web server for SurfOS

## The request

The owner, 2026-10-17: create a worktree off the AI work branch (`ai-dev`) and start to
build out a simple web server that hosts websites off SurfOS: just basic HTML/CSS
applications. The work is done on branch `httpd/main` (from ai-dev 0efbade) in its own
worktree, apart from the other agents' branches; it is merged into ai-dev only at the
owner's word, and nothing is pushed.

## What gets built

| Request | How |
|---|---|
| A web server on SurfOS | `httpd`, a program in `/initrd/bin`, like `telnetd`: it serves a folder over HTTP/1.1 on port 80 |
| Hosting websites | `httpd on /data/www` serves a folder of a mounted USB stick; each folder inside it is a site of its own (`/data/www/blog/` is at `http://<laptop>/blog/`); a folder without an `index.html` is listed, so the sites can be found |
| Basic HTML/CSS applications | Static files with the right types: HTML, CSS, scripts, JSON, text, pictures (PNG, JPEG, GIF, SVG, WebP, icons), fonts, PDF. No server-side programs, no uploads |
| Something to see at once | `httpd on` alone serves `/initrd/www`, a SurfOS-themed sample site (index.html, style.css, wave.svg) that says how to host your own |

Commands:

    httpd on [folder] [port]      serve folder (default /initrd/www) on port (default 80), in the background
    httpd serve [folder] [port]   the same on this console, each request printed; Ctrl+C stops it
    httpd off                     stop the background server
    httpd [status]                whether it runs, and its pid

The folder and the port come in either order: a word of digits is the port. `httpd on`
prints the address to open (`httpd: serving /data/www at http://10.0.0.4/`), or says to
run `dhcp` first. Started in a telnet session, the server ends with the session (the
pseudo-terminal's hangup), and `httpd on` says so.

Decisions (the integrator's, stated to the owner):

* Read-only, static files only. No server-side programs, uploads or logins. Like
  `telnetd`, it never starts by itself.
* Files are read fresh for every request, so an edited page shows on the next reload.
  Responses carry an ETag (size and modification time) with `Cache-Control: no-cache`:
  the browser asks again every time and gets `304 Not Modified` while the file is the
  same. There is no `Date` or `Last-Modified`: SurfOS's clock keeps local time with no
  time zone, which HTTP must not present as GMT.
* Names starting with a dot are neither listed nor served (404). macOS leaves `._*`,
  `.DS_Store`, `.Trashes` and `.fseventsd` on every FAT stick it writes.
* No per-request log in the kernel log: its 16 KB ring would lose the boot and Wi-Fi
  messages after a few hundred requests. The background server logs its start, its stop
  and its errors there; `httpd serve` prints every request on its console.
* One background server at a time; more sites are folders inside the served one.

## Design

`user/httpd/`, three parts, as `user/telnetd/`:

* `main.c`: the commands. `httpd on` finds a running server (`procinfo`: a detached user
  task named `httpd`), checks that the folder is one, calls `tcp_listen()` itself (so
  "port in use" is said at once), then starts the server with `spawnfd()` as this same
  program with the internal word `--server`, the port and the folder, the listening socket
  as its descriptor 0 and `/dev/null` as 1 and 2. A relative folder is made absolute first.
* `server.c`: one `poll()` loop over the listening socket and up to `MAX_CONNS` (6)
  connections; nothing in it waits for one client. A connection reads its request head
  (at most 4 KB), then sends the response: a header, then the body from the file or from
  memory (a listing, an error page), in pieces of up to 8 KB written as far as the
  connection takes them (`POLLOUT`). HTTP/1.1 connections stay open between requests
  (keep-alive; HTTP/1.0 only when asked), and a request that arrived behind another
  (pipelining) is answered after it. Limits:
  * a connection waiting for a request has 10 s to begin it and 10 s from its first byte to
    finish its head (then `408` when part of a request came, or a plain close);
  * a response the client has taken nothing of for 30 s is given up;
  * when all 6 places are taken, a new connection takes the place of the one idle longest;
    when none is idle, it waits in the kernel's backlog until a place is free.
  The 6 places keep within a process's 16 descriptors (a connection and its open file each
  count: with 0, 1, 2 and the kernel log's, all 16).
* `http.c`: the protocol, with no system calls, host-tested in `tests/host/test_httpd.c`:
  finding the end of a request head, parsing it (the request line, origin and absolute
  forms, `Host`, `Connection`, `Content-Length`, `Transfer-Encoding`, `If-None-Match`),
  decoding and normalising the path (`..` refused, dot names hidden), content types,
  the response header, error pages, the HTML of a folder listing (names escaped, links
  encoded, folders first), and making a folder argument absolute.

One kernel change, opt-in: `SYS_listen` takes a second argument, the backlog (0 keeps the
default 4; 8 at most; libsurf's `tcp_listen_backlog()`). httpd asks for 6: its listener, 6
places and 6 waiting are 13 of the 15 sockets programs may have, so telnetd still gets its
listener and a session under a full load (the review's point: 8 would have taken all 15).
With 4, the six
SYNs a browser sends at once lost two to a full backlog before the server could accept
the first: those clients waited for a retransmission, or were reset when their half-open
place went to a later SYN. Everything else keeps 4 (tools/qemu-tcp.py's scenarios count on
it); `nettest sleepsrv <port> <ms> [backlog]` and a new `backlog` TCP scenario test the rest.

Responses: `200`, `301` (a folder asked without its `/`), `304`, `400`, `404`, `405`
(methods other than GET and HEAD, with `Allow`), `408`, `414`, `431`, `500`, `505`. Every
error but 404 closes the connection, as does any request with a body, which is never read.
A file that is shorter when read than when it was looked at ends its connection, since
its `Content-Length` was already sent.

## Checks

* `tests/host/test_httpd.c` (in `make unittest`): request heads whole and in pieces,
  every parse rule and status, path decoding and traversal, content types, header bytes,
  ETag matching, listings, folder arguments.
* The smoke test (`tools/qemu-run.py`, guest port 80 forwarded as `q.ports['www']`):
  status, errors and usage of the commands; the sample site from the host with Python's
  `http.client` (types, HEAD, 304, 404, 301, the listing of `/initrd`, a large file
  compared byte for byte); the protocol (400s, 405, 414, 431, 505, keep-alive, pipelining,
  HTTP/1.0); six idle connections and a seventh served, six unfinished requests and a
  seventh kept waiting, eight clients side by side; the idle and request timeouts; the
  initrd's root on port 8080 through a second forward; a site on the FAT disk (`index.htm`,
  a name with a space, a hidden file and its 8.3 alias) with `httpd serve` printing each
  request and ending on Ctrl+C; a client that stops reading a 2.5 MB file there while others
  are served; `httpd off`; the kernel log.
* `tools/qemu-usb.py`'s usbnet scenario: the sample site over the USB Ethernet adapter.
* `tools/qemu-tcp.py`'s `backlog` scenario: eight whole connections wait, a ninth SYN is
  dropped, the first is served once the program accepts.
* The whole suite at O0 and O2 (unittest, smoke, TCP, USB), then an independent review.

Found on the way: Chrome shows its own error page in place of an error response under 512
bytes, so httpd's error pages are longer than that (a viewport line and a link to the front
page). QEMU's user network takes the connections to a forwarded port one at a time (of two
made in the same instant, one is reset on the host before the guest sees it), so the smoke
test's clients begin a little apart, and the guest's own backlog is the TCP scenario's to
test. Chrome, which opens two connections for a page, fails a first load through such a
port now and then for the same reason: an artefact of the emulator's port forward.

## After the review

An independent review (2026-10-17) found no memory-safety, traversal, framing or poll-loop
defects. It found these, all fixed:

* The backlog of 8 let httpd take every socket programs may have (its listener, 6 places
  and 8 waiting are 15): httpd asks for 6 now, still a browser's six.
* HTTP/1.0 with `Connection: keep-alive, close` kept the connection: close wins now. A HEAD
  with a bad version got an error page with a body: the method is known before the version
  is checked.
* Tests: the keep-alive check could not see a server that closes every connection (it
  compares the connection's own address now, and http.client's dropped one fails it); the
  stalled client's 188 KB could pass through QEMU's and this host's buffers without the
  guest ever waiting (it is a 2.5 MB file on the FAT disk now, `@httpd-slow`); some checks
  connected back to back, which QEMU's port forward resets (every check connects through
  `www_connect()`, 50 ms apart); a `.DS_Store` check proved nothing (dropped), and the 8.3
  alias of a hidden file has a check (`SECRET~1`).
* Two sentences of ARCHITECTURE.md had gone stale (no kernel change, ten at once).
