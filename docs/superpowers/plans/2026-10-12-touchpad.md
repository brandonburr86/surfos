## Controller implementation boundary

`driver/i2cdw.c` supplies a callback-based polled PIO engine with caller-provided
timings. It does not initialize any laptop hardware yet. The platform layer must
first establish the actual firmware device, BAR assignment, power dependencies,
and touchpad address. D3hot-to-D0 alone cannot supply an unassigned BAR.

The matching Intel 8086:34e8/34e9 functions use a 133 MHz input clock in Linux's
LPSS platform data. Once actual resources are known, the LPSS wrapper needs BAR
remapping, reset and power handling before probing the DesignWare component.
The caller must serialize transfers and use the hardware's input-ready signal
when collecting HID reports. No ACPI interpreter or generic PCI allocator has
been added by the PIO engine.

## Hardware export notes

The first diagnostic build booted successfully and all nine SSDTs exported with
valid checksums. DSDT at 0x4bc01000 exceeded or otherwise failed the initial
whole-window mapping check. Its address is about 168 KiB below the XSDT. Export
was changed to checked chunks with a 1 MiB table limit; host tests cover multi-chunk tables up to 1 MiB. QEMU limits injected tables
to 65535 bytes, so its real telnet export test uses a 60 KiB SSDT.
