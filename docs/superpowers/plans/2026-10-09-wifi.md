# Brief: Wi-Fi for SurfOS (the IdeaPad's Intel Wireless-AC 9560)

Requested by the owner on 2026-10-06 (tabled the same day; `docs/WIFI-PLANNING.md`), resumed
on 2026-10-09: SurfOS reaches the network through the laptop's internal Wi-Fi card. A command
lists the networks in range, joins one with its password, then gets an address by DHCP.

## Decisions (the owner, 2026-10-09: "go with what you recommend")

* **WPA2-Personal first** (RSN, AKM PSK, CCMP pairwise and group). WPA3 (SAE and protected
  management frames) is a later milestone; HouseOfBurr's 2.4 and 5 GHz bands are WPA2.
* **Intel's firmware on the stick.** The build downloads the two `.ucode` files and Intel's
  licence (`LICENCE.iwlwifi_firmware`) from linux-firmware at a pinned commit, checks their
  SHA-256, and puts them in the USB image's initrd (`/initrd/lib/firmware/`). They are never
  committed.
* **Development on the laptop over the network.** The integrator (Claude, on the owner's Mac)
  telnets into the laptop to test and read logs; new builds go to the laptop over the network
  (track D below), so the owner writes the stick once and keeps the laptop plugged in.
* **The Wi-Fi password** is never asked for, written to a file, logged, or put in a chat. The
  owner types it at the laptop (`wifi join`, hidden input). SurfOS keeps only the derived key
  (PMK) and only in RAM. Agents test WPA2 on the host (test vectors, a simulated access point);
  the first WPA2 join on the laptop happens with the owner typing the password.

## Milestones

| | Done when (on the laptop) |
|---|---|
| **W0** development loop | a build from the Mac boots on the laptop without the owner touching it: pushed over the network to the data stick, the laptop rebooted, GRUB's development entry, `eth0` and `telnetd` up by themselves |
| **W1** the card starts | `wifi up`: the firmware loads, the card reports ALIVE and its firmware version, its MAC address read from its NVM; `wifi down` and `wifi up` again |
| **W2** scan | `wifi scan` lists the networks in range: SSID, BSSID, channel, band, signal, security; HouseOfBurr on 11 and 157 among them |
| **W3** join | `wifi join xfinitywifi` (open) then `dhcp wlan0`: an address, frames both ways; then `wifi join HouseOfBurr` (WPA2, the owner types the password), `dhcp wlan0`, `ping 10.0.0.1` through wlan0 |
| **W4** robustness | the access point's group key renewal, deauthentication, beacon loss and reconnect, `wifi leave`/`down`; tests and docs |
| **W5** (later) | WPA3-SAE with protected management frames; power saving |

## Architecture

```
wifi (shell/wifi.c)        the kernel command: up, down, scan, join <ssid> [bssid], status, leave
station layer (net/wlan/)  scan list, open authentication and association, the supplicant, wlan0 as a netdev,
                           802.11 data frames <-> Ethernet II (LLC/SNAP), routing with two interfaces
supplicant (net/wlan/wpa.c) PSK -> PMK (PBKDF2), the 4-way and group key handshakes, the RSN element
crypto (lib/crypto/)       SHA-1, SHA-256, HMAC, PBKDF2, the 802.11 PRF, AES-128, AES key wrap, a CSPRNG
Intel driver (driver/wifi/) the 9560 on Qu: PCI, the gen2 transport (context info, TFH TX queues, multi-queue RX,
                           paging), firmware TLV parsing and loading, firmware commands (MVM API 77), scan,
                           MAC/PHY/binding/station/session protection, TX and RX, keys
```

The interfaces between the layers are fixed by the foundation commit:

* `include/net/wlan.h`: the station layer and its chip drivers (`struct wlan_hw_ops`,
  `wlan_register()`, `wlan_rx()`, `wlan_scan_done()`, `wlan_link_lost()`).
* `include/net/wpa.h`: the supplicant, as the station layer uses it.
* `include/crypto/crypto.h`: the crypto library.

Read their comments; they are the contract. A track that needs one changed says so to the
integrator, who changes it for everyone.

### Threads and context

* The Intel driver polls its device from its own kernel thread (no interrupts at first; MSI
  through the local APIC may come later) and delivers every received 802.11 frame with
  `wlan_rx()`, always from task context, never from an interrupt handler.
* `wlan_rx()` copies the frame into the station layer's queue and returns; the station layer's
  own thread (`wlan`) parses scan results, runs authentication, association and the supplicant,
  and hands data frames to the IP stack as Ethernet frames (`netdev_rx()`).
* `tx_data()` and `tx_mgmt()` never wait (they queue or drop) and may be called with `net_lock`
  held; every other operation may wait for the firmware and is called only from the `wlan`
  thread or a command's task, never with `net_lock` held.

### Track D: the development loop (W0)

* **GRUB:** when a disk other than the boot drive holds `/surfos-dev/surfos.bin` and
  `/surfos-dev/initrd.tar` (`search --file`), a first entry "SurfOS (development build from the
  data stick)" boots them with `profile=laptop autonet` and is the default; every other entry
  stays as it is. Without such a disk the menu is unchanged (`tools/qemu-usb.py` picks entries
  by position).
* **`autonet`** (a kernel word): a kernel thread waits up to 90 seconds for an interface with a
  link, runs DHCP on it, then starts `/initrd/bin/telnetd on` (its output on F1); every step is
  logged. The boot drive stays read-only and nothing is mounted by itself.
* **`rx <port> <path>`** (a user program): listens on the port, takes one connection within two
  minutes, writes everything to `<path>.part`, renames it to `<path>`, prints the size and the
  CRC-32; nothing else.
* **`/initrd/etc/build-id`**: the git revision (with `-dirty`) and the UTC build time.
* **`tools/devloop.py`** (on the Mac): `deploy` builds nothing itself; it takes `surfos.bin` and
  `initrd.tar` of a build, finds the laptop (10.0.0.4 by default; else the host on 10.0.0.0/24
  that answers telnet), mounts the data stick (the USB disk that is not the boot drive, by
  `lsblk`), pushes both files with `rx` (checking the CRC-32), ejects, reboots, waits for telnet
  and checks the build id; `run` runs commands and prints their output; `log` prints `dmesg`.
* **Tests:** a `devloop` scenario in `tools/qemu-usb.py` (a boot image and a FAT32 data stick
  holding a development build: the development entry boots it, `autonet` brings up the USB
  network and telnetd, a push with `rx` and a reboot bring up the new build id); smoke steps
  for `rx`; nothing changes when there is no data stick.
* **The owner, once:** writes the new image, keeps the boot stick, a FAT32 data stick and the
  Ethernet adapter plugged in, and sets the laptop to boot from USB first.

### Track C: crypto and the supplicant

* `lib/crypto/`: SHA-1, SHA-256, HMAC-SHA1/-SHA256, PBKDF2-SHA1, the 802.11 PRF (SHA-1),
  AES-128 (encrypt and decrypt), AES key wrap and unwrap (RFC 3394), constant-time compare,
  wiping, and `crypto_random()`: RDRAND when CPUID says so (Ice Lake has it), mixed with the TSC
  and timer jitter into an HMAC-DRBG (SHA-256); never a fixed seed.
* `net/wlan/wpa.c`: the passphrase (8-63 characters) to the PMK, our RSN element (CCMP/CCMP,
  PSK, no MFP), the 4-way handshake as the supplicant (SNonce, PTK by the PRF, MIC with
  HMAC-SHA1-128, key descriptor version 2, message 3's RSN element checked against the beacon's,
  the GTK from the key data unwrapped with the KEK), the group key handshake, replay counters,
  timeouts; keys reach the driver through the station layer's `install_key`; secrets wiped.
* Tests (`make unittest`): FIPS 180 and RFC test vectors for SHA and HMAC, RFC 6070 for
  PBKDF2, IEEE 802.11-2016 Annex J for the PSK and the PRF, RFC 3394 for key wrap, and a
  simulated access point (an authenticator written in the test) running complete handshakes
  against `wpa.c`, including bad MICs, replays, wrong RSN elements and a group key renewal.

### Track S: the station layer and `wifi`

* Frames (`net/wlan/ieee80211.c`, pure, host-tested): beacons and probe responses parsed into
  `struct wlan_bss` (SSID, channel from the DS element or the receive channel, RSSI, rates,
  HT/VHT seen, security from the RSN element and the privacy bit); probe, authentication,
  association and deauthentication frames built; data frames to and from Ethernet II (To DS,
  From DS, LLC/SNAP, QoS data); EAPOL (ethertype 0x888e) to the supplicant.
* The station (`net/wlan/wlan.c`): `wlan_register()` makes `wlan0` (a netdev named so), the
  `wlan` thread, the scan list (aged), joining (open authentication, association with our
  rates, the RSN element, HT capabilities when the AP has them), the supplicant for WPA2, link up
  only once the keys are in, deauthentication and link loss (down, then a new join after a while),
  `wifi leave`.
* `shell/wifi.c`: `wifi up | down | scan | join <ssid> [bssid] | status | leave`; `join` asks the
  password with the input hidden and its echo off (a new `shell_ask_secret()`), turns it into
  the PMK at once and wipes it; output for scans sorted by signal.
* Two interfaces: `netdev_register()` keeps a name a driver set (`wlan0`); `ip_route_dev()`
  chooses the interface by the source address when one is given, then by the destination's
  subnet (in the order the interfaces registered), so `eth0` and `wlan0` can both be on
  10.0.0.0/24: a TCP connection made to eth0's address keeps answering through eth0 (the
  telnet session the integrator uses), and `ping <address> [count] [interface]` can force an
  interface. `dhcp wlan0` works as `dhcp eth0` does.
* Tests: the frame code against hand-built and captured frames; the station against a simulated
  chip driver (`wlan_hw_ops` in the test) that answers scans, authentication and association,
  and a simulated access point using track C's supplicant (until it lands, against its header).

### Track I: the Intel driver

* **References** (kept in the integrator's scratchpad, never committed): OpenBSD's
  `sys/dev/pci/if_iwx.c`, `if_iwxreg.h`, `if_iwxvar.h` (ISC; parts BSD from Intel) as the main
  guide: it drives this family with firmware API 77; Linux's
  `drivers/net/wireless/intel/iwlwifi/` (GPL-2.0 or BSD-3-Clause) where `iwx` has no entry (the
  Qu B0 step with JF). Code written from them keeps their copyright and licence notices in the
  file header; register and structure definitions may be transcribed with those notices.
* **Firmware:** `tools/fetch-firmware.py` downloads `iwlwifi-Qu-b0-jf-b0-77.ucode`,
  `iwlwifi-Qu-c0-jf-b0-77.ucode` and `LICENCE.iwlwifi_firmware` from linux-firmware
  (`gitlab.com/kernel-firmware/linux-firmware`) at a pinned commit into `firmware/` (ignored by
  git), checks SHA-256 values written in the tool, and the initrd carries them under
  `/lib/firmware/`. The TLV parser is host-tested against the real files.
  *Done 2026-10-10:* tag 20260916 (commit ab23307c); `devenv/build-usb.sh` runs the tool first
  (without a network it checks the files already there; without them the image is built with no
  Wi-Fi firmware). Only the USB image's initrd (`build/O<n>/initrd.tar`, the one `devloop.py
  deploy` sends) carries them, about 2.6 MB; the QEMU initrd (`build/images/`) has no Intel card
  to load them into and is unchanged. `driver/wifi/iwl_fw.c` reads the container
  (`include/sys/iwl_fw.h`) without copying it; `tests/host/test_iwlfw.c` checks it on hand-made
  and broken files and on both real ones: "release/core74::8dbafb52", version 77.8dbafb52.0,
  48 runtime sections (12 for the first CPU, 14 for the second, 20 paged: 1.3 MB in all), two
  CPUs, 67 scan channels, LAR, UMAC scan, TLC offload and session protection, 192 command
  versions, error logs at 0x00880128 (UMAC) and 0x004adfc0 (LMAC). B0 and C0 differ only in
  the second CPU's sections (16 bytes).
* **Bring-up (W1):** find 8086:34f0 (the laptop profile only; a driver table entry that does
  nothing more at boot than finding and naming the device), map BAR0, enable memory and bus
  master, read CSR_HW_REV (the step: B0 or C0) and, after the NIC is prepared, CSR_HW_RF_ID;
  choose the firmware file; parse its TLVs; build the context info (firmware sections in DMA
  memory, paging blocks, the RX queue's free, used and status buffers, the command queue);
  start the firmware; wait for ALIVE; send the init commands in iwx's order (as API 77 needs
  them) up to NVM_GET_INFO for the MAC address; `wlan_register()`.
  *Done 2026-10-10 (step 2), on the laptop:* `driver/wifi/iwl.c`, the driver table's `iwlwifi`
  (profile=laptop only). At boot: 00:14.3, BAR0 0x81220000, CSR_HW_REV 0x00000332 (the Qu MAC,
  C step: bits 1-0 hold the step in this family), CSR_HW_RF_ID 0x00105110 (JF2, step B), so
  `iwlwifi-Qu-c0-jf-b0-77.ucode`; wlan0 registered. `wifi up` powers the card up (iwx_start_hw()
  for an integrated 22000-family card), finds the radio switch on, reads a valid MAC address from
  the card's CSR registers already before the firmware runs, reads and checks the firmware file
  from the initrd, then stops the card and fails with ENOSYS until the firmware load (step 3).
  The other drivers' write to the old retry-timeout register 0x41 is left out: on this card 0x41
  is the PCI Express capability's next pointer.
* **Scan (W2), join and data (W3):** the commands at the versions the firmware's
  `IWL_UCODE_TLV_CMD_VERSIONS` asks for; received frames to `wlan_rx()` with channel, RSSI and
  the decryption status; TX queues allocated per station and TID as the firmware requires;
  CCMP keys installed in the firmware; the firmware's rate control (TLC); no power saving.
* **DMA:** the 1:1 DMA heap is 5 MB and shared with USB (`include/mm/memory.h`, `PHEAP_SIZE`);
  keep the receive buffers few (64 is plenty), free the firmware copies the card no longer
  needs after ALIVE (keep paging), and if it must grow, grow it (a memory-setup change: test-usb
  at -O0 and -O2).
* **Polling** from the driver's thread: the RX queue's status, the interrupt cause registers as
  status; a stuck firmware is reported (its error log read from SRAM) and `wifi down` resets the
  card.
* **Hardware tests** go through track D's loop once it is deployed (the integrator says when).

## Rules for every track

* Work only in your worktree and branch; other tracks' files are off limits except where this
  brief names a shared file (the harnesses' step lists, the Makefile's lists: add your lines in
  a block of your own).
* Every commit builds and passes `make unittest` and `make test-all`; a change to the boot path,
  memory setup, console, USB or anything `profile=laptop` touches also passes `make test-usb` at
  -O0 and -O2. Use `SURFOS_VOLUME=surfos-<track>` with `devenv/build.sh`.
* Kernel code follows `CLAUDE.md`: statuses, `curTask->con`, no shared statics, `shell_ask()`,
  every hardware wait bounded, nothing on the internal disk, the boot drive only read.
* **The laptop** (10.0.0.4, telnet, no password) belongs to one track at a time, as the
  integrator assigns it: track D until W0 is deployed, then track I. Nobody else connects.
  Never format, partition or write any disk on it except the data stick's `/surfos-dev/` folder
  (and files a test names under it); never send `reboot` except through `tools/devloop.py`.
* Never ask for, type, log or store a Wi-Fi password. Open networks (xfinitywifi) may be joined
  for tests; HouseOfBurr is joined only by the owner.
* Keep the 2004 file headers and style; new files use the same header block with the date.
  Small commits, one topic each, ending with the co-author line. Never push; never touch
  `master`, `04-source-recovered/` or `01-scans-original/`.
