# Brief: one USB stick for booting and for files

Asked for and approved by the owner on 2026-10-17. Until now the IdeaPad needed two sticks:
the boot stick, written with the image (GPT, FAT32 labelled SURFOSUSB, which SurfOS only
reads), and the data stick (the 30 GB *USB Disk 2.0*, MBR, FAT32), which holds the owner's
files and the development build in `/surfos-dev/`. The owner asked whether the data stick
itself could boot, so that one stick serves the whole project and a new kernel is a file
copied onto it rather than an image flashed.

**Status, 2026-10-17:** done on the `ai-dev` line under emulation (`make test-usb` scenario
`onestick` at -O0 and -O2, the smoke test's `test_boot_volume`, `make unittest`,
`make test-mkusb`); the test on the laptop is pending. The user guide is
[USB-BOOT.md section 14](../../USB-BOOT.md#14-one-stick-for-everything), the design
[ARCHITECTURE.md section 16](../../ARCHITECTURE.md), "One stick".

## Why it works

UEFI firmware starts `\EFI\BOOT\BOOTX64.EFI` from any FAT partition of a removable drive,
MBR or GPT, whatever its label (Windows installer sticks are laid out this way). SurfOS's
boot loader already found its own partition through GRUB's `$cmdpath` rather than by
label. Before any code was written, the release image's six files, copied as plain files
onto an image shaped like the data stick (MBR, one FAT32 partition, 16 KB clusters),
booted under OVMF; only the menu and the boot drive rule needed changing.

## Decisions

| Question | Decision |
|---|---|
| May SurfOS write to the stick it booted from? | **Yes, its files** (the owner's approval, 2026-10-17, of a change to rule 3 of the M9 safety model). `fdisk` and `mkfs` still refuse it. The flashed SURFOSUSB image stays read-only. |
| How SurfOS knows its stick | GRUB passes the serial number of the FAT volume the menu was started from (`probe --fs-uuid`) as `bootvol=5D0F-0901` on every entry. No label to set, nothing for the owner to remember. |
| What the stick holds | The image's six files at their paths, plus `/surfos-dev/` (the development build, the menu's first entry). `boot/` is the known-good fallback ("SurfOS"). |
| Updating | Two files together into `/surfos-dev/`: over the network (`tools/devloop.py deploy`, unchanged for the owner) or on the Mac (`tools/stick.py update`, or Finder). |
| Rescue | The flashed SURFOSUSB stick, which SurfOS never writes, is kept. |

## What changed

* `boot/grub-usb.cfg`: `/surfos-dev/` on the menu's own partition first, then the other
  disks as before; the title says which ("from this stick" or "from the data stick");
  `bootvol=$surfos_bootvol` on every `multiboot2` line. `tools/mkusb.py`: `probe` in
  BOOTX64.EFI; `--stick-dir` writes the files as a folder (`build/usb/stick/`), listed in
  the manifest, replaced as a whole, never over a folder holding anything else.
* Kernel: `bootinfo_arg()` (`kernel/multiboot2.c`), `part_fat_serial()` and
  `part_parse_serial()` (`driver/parttab.c`, host-tested), the boot volume in
  `bdev_scan_partitions()` (`driver/part.c`): the disk and its partitions get
  `bdev_boot_drive`, the volume itself `bdev_boot_volume`; SURFOSUSB wins.
  `bdev_mount_readonly()` (`driver/bdev.c`) is the one mount rule, used by `mount` and
  `init_fs()`; `lsblk` says `boot drive: writable` or `mounted (boot drive)`.
* `tools/devloop.py`: deploys onto the writable boot volume first, the order GRUB looks in.
* `tools/stick.py`: `check`, `install`, `update`, `kit`. Only an external FAT volume (diskutil
  on macOS, mounts and sysfs on Linux); each file checked against the manifest, written as
  `.new`, read back, renamed in order (the boot loader last; the initrd before the kernel).
* Tests: `onestick` in `tools/qemu-usb.py` (the stick alone, the menu, `bootvol=`, `lsblk`,
  the refusals, a read-write mount, `devloop deploy` onto the same stick and the reboot,
  the fallback entry, then the stick read back here and checked by fsck_msdos and
  fsck.fat); `test_boot_volume` in the self test (the smoke test passes a `bootvol=`);
  `tests/test_stick.py`; new cases in `test_part`, `test_bootinfo`, `test_devloop.py` and
  `test_mkusb.py`.

## Open

* The laptop: does its firmware offer the data stick by itself with USB first, or only
  through F12? Record it in the hardware record.
* A stick whose boot files predate this work passes no `bootvol=`: SurfOS then does not
  know it as the boot drive, and `fdisk` and `mkfs` would allow it. `tools/stick.py
  install` brings the files up to date.
