# Brief: one USB stick for booting and for files

Asked for and approved by the owner on 2026-10-17. Until now the IdeaPad needed two sticks:
the boot stick, written with the image (GPT, FAT32 labelled SURFOSUSB, which SurfOS only
reads), and the data stick (the 30 GB *USB Disk 2.0*, MBR, FAT32), which holds the owner's
files and the development build in `/surfos-dev/`. The owner asked whether the data stick
itself could boot, so that one stick serves the whole project and a new kernel is a file
copied onto it rather than an image flashed.

**Status, 2026-10-17:** done under emulation on branch `stick/main` (from `ai-dev`): the
smoke test with `test_boot_volume`, `make unittest` and `make test-mkusb`, and `make
test-usb` including the new scenarios `onestick` and `twosticks`, at -O0 and -O2. Two
independent reviews, of the feature and of its fix round, found problems that are fixed
(below). The test on the laptop is pending. The user guide is
[USB-BOOT.md section 14](../../USB-BOOT.md#14-one-stick-for-everything), the design
[ARCHITECTURE.md section 16](../../ARCHITECTURE.md), "One stick".

## Why it works

UEFI firmware starts `\EFI\BOOT\BOOTX64.EFI` from any FAT partition of a removable drive,
MBR or GPT, whatever its label (Windows installer sticks are laid out this way). SurfOS's
boot loader already found its own partition through GRUB's `$cmdpath` rather than by
label. Before any code was written, the release image's six files, copied as plain files
onto an image shaped like the data stick (MBR, one FAT32 partition, 16 KB clusters),
booted under OVMF; only the menu and the boot drive rule needed changing.

## Decisions

| Question | Decision |
|---|---|
| May SurfOS write to the stick it booted from? | **Yes, its files** (the owner's approval, 2026-10-17, of a change to rule 3 of the M9 safety model). `fdisk` and `mkfs` still refuse it. The flashed SURFOSUSB image stays read-only. |
| How SurfOS knows its stick | GRUB passes the serial number of the FAT volume the menu was started from (`probe --fs-uuid`) as `bootvol=5D0F-0901` on every entry. No label to set, nothing for the owner to remember. |
| What the stick holds | The image's six files at their paths, `/surfos-dev/` (the development build, the menu's first entry) and `/boot/ONE-STICK.txt`, the marker without which GRUB does not look in its own `surfos-dev`. `boot/` is the fallback ("SurfOS"). |
| Updating | Two files together into `/surfos-dev/`: over the network (`tools/devloop.py deploy`, unchanged for the owner) or on the Mac (`tools/stick.py update`, or Finder). `install` keeps a good fallback (a whole build whose kernel knows `bootvol=`) and replaces any other; `install --fallback` replaces it always. |
| Rescue | The flashed SURFOSUSB stick, which SurfOS never writes and `tools/stick.py` refuses, is kept. |

## What changed

* `boot/grub-usb.cfg`: on a stick with `/boot/ONE-STICK.txt`, `/surfos-dev/` on the menu's
  own partition first, then the other disks as before; the title says which ("from this
  stick" or "from the data stick"); `bootvol=$surfos_bootvol` on every `multiboot2` line.
  `tools/mkusb.py`: `probe` in BOOTX64.EFI; `--stick-dir` writes the files as a folder
  (`build/usb/stick/`, with the marker, which the image does not get), listed in the
  manifest, replaced as a whole, never over a folder holding anything else
  (`--check-stick-dir`, which `devenv/build-usb.sh` asks before it replaces its copy).
* Kernel: `bootinfo_arg()` (`kernel/multiboot2.c`), `part_fat_serial()` (read whatever the
  extended boot signature says, as GRUB reads it) and `part_parse_serial()`
  (`driver/parttab.c`, host-tested), the boot volume in `bdev_scan_partitions()`
  (`driver/part.c`): the disk and its partitions get `bdev_boot_drive`, the volume itself
  `bdev_boot_volume`; SURFOSUSB wins. `bdev_mount_readonly()` (`driver/bdev.c`) is the one
  mount rule, used by `mount` and `init_fs()`; `lsblk` says `boot drive: writable`,
  `mounted (boot drive)`, or `boot drive: read-only` behind a write-protect switch.
* `tools/devloop.py`: deploys onto the writable boot volume first, the order GRUB looks in;
  refuses `--stick` naming another disk then, and a boot volume without the marker.
* `tools/stick.py`: `check`, `install [--fallback]`, `update`, `kit`. Only an external FAT
  volume (diskutil on macOS, mounts and sysfs on Linux), never the flashed SURFOSUSB stick,
  never over another system's boot loader, menu or module list (they are recognised by
  content, names matched regardless of case as FAT does); each file checked against the
  manifest, written as `.surfos-new`, read back, renamed in order (the boot loader and then
  the menu last, so an older loader, which has no `probe`, keeps its own menu when a stick is
  pulled out halfway; the initrd before the kernel); on a failure its new files and empty
  folders go again. It marks a kernel from before 10/17/26 (one without the word
  `bootvol=`), which would not know the stick, and replaces such a fallback.
* Tests: in `tools/qemu-usb.py`, `onestick` (the stick as `tools/stick.py` lays it out,
  alone: the menu, `bootvol=`, `lsblk`, the refusals, a read-write mount, `devloop deploy`
  onto the same stick and the reboot, the fallback entry, then the stick read back here
  and checked by fsck_msdos and fsck.fat) and `twosticks` (a SURFOSUSB-labelled stick with a
  stale `surfos-dev` beside a data stick; a one-stick beside a data stick); in the self
  test, `test_boot_volume` (the smoke test passes a `bootvol=` and requires its checks);
  `tests/test_stick.py`; new cases in `test_part`, `test_bootinfo`, `test_devloop.py`
  (a fake session for the marker refusal) and `test_mkusb.py`.

## The review (2026-10-17)

An independent reviewer read the first commit. Fixed since:

1. A `surfos-dev` folder on the flashed image would have been booted first, though SurfOS
   can never update it: the marker now limits the menu's own-partition look to sticks made
   for it, and `tools/stick.py` refuses SURFOSUSB. (Probing the label in GRUB was rejected:
   `probe --label` prints an error on every boot from an unlabelled stick.)
2. `tools/stick.py install` would have replaced another system's boot files at the same
   paths: it now refuses, naming them.
3. `devloop.py deploy --stick` could name a stick GRUB would not start a build from.
4. A second `install` replaced the fallback: it now keeps it unless `--fallback`.
5. Docs, untested paths (whole-disk volume, two sticks, the tool's own output booted),
   the mount note under `mount -r`, the serial number without the extended boot signature,
   empty folders and `.new` names left by a failed install, `/boot/firmware` on Linux.

A second reviewer read the fix round. Fixed since:

1. Keeping the fallback could keep a kernel from before this work, which does not know the
   stick: under the "SurfOS" entry `fdisk` and `mkfs` would then have been allowed on it. A
   fallback is kept only when its kernel knows `bootvol=`.
2. The `twosticks` scenario could not pass: `tools/mkimage.py` gave every image the same
   serial number, so the kernel took the data stick for the boot volume too (and protected
   both, as it should for two sticks with one serial number). Each test stick has its own now.
3. A write-protected boot stick (`boot drive: read-only`) is refused by `devloop.py` with what
   to do, instead of a build pushed where GRUB does not look first.
4. `tools/stick.py check` warns when the flashed stick holds the marker (copied by hand), and
   section 14 says never to do that; the `--stick` refusal says when it applies; the menu is
   renamed after the loader; tests for the marker's enclosure, the deploy past the marker,
   NTFS and exFAT boot sectors; docs.

A third, narrow review read that round. Fixed since: a fallback is kept only when its
kernel and initrd are the ones its `BUILD-INFO.txt` names by SHA-256 (so a pair an
interrupted copy mixed, or a file cut short, is written again), an unreadable one is not
kept, and `--fallback` never reads it; `devloop.py` checks for two sticks with one serial
number before the write-protect switch, and its `--stick` refusal says what it rests on;
the messages and docs about an interrupted install say exactly what it leaves; more tests
(a mixed or cut fallback, an unreadable one, the menu kept on an older stick pulled out at
the menu, an initrd whose build id is a folder, the serial number of an image).

## Open

* The laptop: does its firmware offer the data stick by itself with USB first, or only
  through F12? Record it in the hardware record.
* A stick whose boot files predate this work passes no `bootvol=`, and a build older than
  10/17/26 ignores it: either way SurfOS then does not know the stick as its boot drive, and
  `fdisk` and `mkfs` would allow it. `tools/stick.py check` marks such builds, `install`
  brings the loader and the menu up to date and replaces such a fallback, and `update` and
  `devloop.py deploy` say so when they put such a build into `surfos-dev`.
* The flashed stick with the stick folder copied onto it by hand (against section 14) would
  start its own, never updated `surfos-dev`; `check` warns about it. Writing an image-only
  file that the menu tests for would close it for new images only, not for those already
  flashed, so it was not done.
