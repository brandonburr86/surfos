# Brief: network tools, files to and from other computers

## The request

The owner, 2026-10-24: build out more useful networking applications, for example for
transferring files remotely, some sort of file transfer protocol, so that files go back and
forth between SurfOS and other computers on the network, such as the owner's MacBook Pro;
then other capabilities and tools like that to enhance what SurfOS does on the network. Build
it as a worktree. The work is done on branch `nettools/main` (from ai-dev 0d641d4) in its own
worktree, `06-restoration-nettools` beside the main checkout; it is merged into ai-dev only
at the owner's word, and nothing is pushed.

## What gets built

| Request | How |
|---|---|
| A file transfer protocol, both ways with the Mac | `ftpd`, an FTP server in `/initrd/bin`, laid out as `telnetd` and `httpd`: the Mac copies files from SurfOS and onto it with what it has (Finder's Go > Connect to Server reads; `curl` and Python's `ftplib` read and write) or with any FTP program (Cyberduck, FileZilla, Transmit) |
| Transfers started on SurfOS | `nc`, the netcat of SurfOS: a connection to any address and port, or one that comes to a port, with what is typed or a file going out and what comes back printed or saved; the Mac's own `nc` is the other end, either way round |
| What they need of the kernel | the sockets' half-close (`shutdown()`, which programs lacked), both ends of a connection (`tcp_addrs()`: a passive reply names the address the client reached), and a connection opened without waiting for its handshake (`tcp_connect_start()`: active mode never holds the server's loop) |
| Other network tools | `nc -z` (which ports of a computer are open); a fix of `httpd serve`, which stopped answering at the pager's `--More--` after 22 requests |
| Files from the web, and from the Mac without an FTP server | `fetch` (10/25/26), a downloader: `http://` and `https://` into a file, resumed where it stopped; the Mac serves a folder with `python3 -m http.server` |

## Decisions (the integrator's, stated to the owner)

* **FTP**, because the Mac speaks it with nothing installed (Finder reads, `curl` writes,
  Python's `ftplib` both) and every FTP program on every system speaks it. No SFTP or FTPS:
  SurfOS has no SSH, and TLS for a server would need a certificate the Mac trusts.
* **No logins, by the owner's earlier choice for telnetd**: any user name and password are
  taken. Like `telnetd` and `httpd`, `ftpd` never starts by itself, and it reaches only the
  files of the folder it was given (`/` by default: every mounted volume at its own path, so
  `ftp://<laptop>/data/notes.txt` is `/data/notes.txt`). It reads and writes, since files are
  to go both ways; `ftpd on -r` serves a folder read-only. What can be written is what SurfOS
  writes anyway: mounted FAT volumes (the boot drive only in the one-stick case the owner
  approved), never the initrd. `/dev` and the network manager's short mount `/.netman` are
  neither listed nor reached.
* **Open networks.** A writable server with no logins is what the network manager already keeps
  off networks anyone may join: while an `ftpd` runs, the Wi-Fi keeper joins no open network by
  itself, as for `telnetd` (`kernel/netman.c`), and says why; `wifi join` and `wifi save` of an
  open network say so too.
* **Both data connection modes.** Passive (PASV, EPSV): a listener on a port of the passive range
  (50000-50999 unless told) for each transfer, the connection taken only from the client's own
  address. Active (PORT, EPRT), which Finder tries first and the `ftp` of Windows only speaks: to
  the client's own address and ports from 1024 only (no FTP bounce), connected to without a wait
  (the kernel's new `CONNECT_NOWAIT`), so a client whose firewall drops it holds up no other.
  `-a address` names the address passive replies give, for a server behind a router (and for
  QEMU's user network in the tests).
* **Times.** SurfOS's clock is the CMOS clock with no time zone (as httpd's brief says). `LIST`
  is `ls -l`'s format, whose times are the server's local time by convention, so it shows them
  as they are. What FTP defines in UTC (`MDTM`, the `modify` fact of `MLSD`) is not offered,
  rather than passing local time off as UTC; `MLSD` and `MLST` answer without it and are not
  advertised in `FEAT`, so GUI clients list with `LIST` and show the times as they are.
* **Hidden files.** `LIST` and `NLST` leave out names starting with a dot unless asked (`-a`),
  as `ls` and the usual servers do (macOS leaves `._*` and `.DS_Store` on FAT sticks); `MLSD`,
  for programs, lists everything, so a client deleting a folder can empty it; RMD's refusal of
  a folder that holds only hidden names says so. Every name can be reached by name.
* **Uploads write in place**, as vsftpd does: `STOR` writes the file it names (a failed upload
  leaves the part that came, and `REST` resumes it, the file cut at the offset first), with no
  temporary name renamed over it, so the FAT rename of a file over another (ARCHITECTURE.md
  section 10) is not needed for every upload. `RNTO` renames as `mv` does.
* **Text mode** (`TYPE A`) converts line ends (LF on SurfOS, CR LF on the network) for the
  clients that ask for it (FileZilla does for `.txt` and `.html` by default); `TYPE I` sends the
  bytes as they are. Listings are CR LF lines either way.
* **nc ends when both ways have.** The input's end is sent as the half-close; the other end's FIN
  says it has sent all it will; `nc` ends when both have, or at that FIN when the input is typed
  (the console has no end of its own). That is the Mac's `nc` too.
* **Kernel changes**, small and opt-in: `SYS_shutdown`, `SYS_sockaddr`, `SYS_connect`'s
  `CONNECT_NOWAIT` (libsurf passes 0, so every program that connects is as it was), TIME_WAIT
  keeping what a half-closed connection's program has not read, the write on a connection still
  in its handshake waiting for it, ENOTSOCK, and the network manager's rule above.

## ftpd

Commands:

    ftpd on [-r] [-a address] [folder] [port] [first-last]   serve folder (default /) on port (21), in the background
    ftpd serve [the same]                                    on this console, each command printed; Ctrl+C stops it
    ftpd off                                                 stop the background server
    ftpd [status]                                            whether it runs, and its pid

The words after `on` and `serve` come in any order: `-r` read-only, `-a` and an address, a
word of digits the port, two numbers joined by `-` the passive range, anything else the folder
(relative to the current directory). `ftpd on` prints the address to give a client (`ftpd:
serving / at ftp://10.0.0.4/ (read-write)`), or says to run `dhcp` first. Started in a telnet
session, the server ends with the session, and `ftpd on` says so.

`user/ftpd/`, three parts, as `user/httpd/`:

* `main.c`: the commands, as httpd's: the running server is a detached user task named `ftpd`;
  `on` takes the port itself (so "in use" is said at once) and starts the server with
  `spawnfd()` as this program with the internal word `--server`, the listening socket as its
  descriptor 0 and `/dev/null` as 1 and 2.
* `server.c`: one `poll()` loop over the listening socket and up to six sessions; nothing in it
  waits for one client. A session reads its commands a line at a time (Telnet's IAC sequences
  taken out, as RFC 959's control connection is Telnet's), answers them through a buffer
  written on `POLLOUT`, and has at most one data connection: a passive listener, the connection
  it accepted, or the address of `PORT`. A transfer moves a piece of up to 8 KB at a time, as
  far as the connection takes it; a listing is made in memory, then sent. While a transfer
  runs the control connection is still read, for `ABOR` (also as Python's `ftplib` sends it,
  as urgent data that comes in line) and `STAT`; other commands wait their turn, so the replies
  keep the order of the commands. A client that closes its side of the control connection has
  what it sent run and answered. Limits: a session that sends no command for 5 minutes is
  closed (421), a data connection that does not come within 30 s is given up (425), as is a
  transfer that moves nothing for 60 s (426); a seventh session is told 421.
* `ftp.c`: the protocol, with no system calls, host-tested in `tests/host/test_ftp.c`: the
  control stream (lines, Telnet sequences, lines too long, NUL), commands and their arguments,
  paths (the session's directory, `..` held at the folder served, the real path, the paths
  never reached), `PORT`, `EPRT`, `PASV` and `EPSV` texts, the `LIST`, `NLST` and `MLSD` lines,
  line ends of text mode, quoting a path in a 257 reply, the reply for a failed call (errno).

Commands of the protocol: `USER PASS ACCT QUIT REIN NOOP SYST FEAT OPTS HELP STAT SITE PWD CWD
CDUP TYPE MODE STRU ALLO PASV EPSV PORT EPRT LIST NLST MLSD MLST SIZE RETR STOR STOU APPE REST
ABOR DELE MKD RMD RNFR RNTO HOST CLNT` and the `X` forms `XPWD XCWD XCUP XMKD XRMD`; `AUTH`,
`MDTM`, `MFMT` and the rest are refused as not implemented (502), so clients go on without them.

## nc

    nc [-v] [-c] [-w seconds] <host> <port>   a connection to host (an address or a name) and port
    nc [-v] [-c] [-w seconds] -l <port>       wait for one connection to port
    nc [-v] -z <host> <port>...               which ports are open (a connection made and closed at once)

Lines typed (or a file given with `<`) go out; what comes back is printed (or saved with
`>`), byte for byte. So either side sends a file: `nc -l 9000 > file` on the receiving side,
`nc <address> 9000 < file` on the sending one, SurfOS's `nc` or the Mac's. `-v` says both ends
and how the connection ended, `-c` sends CR LF for each line typed (a mail or web server
talked to by hand), `-w` ends a connection silent that long.

## Found on the way

* **Finder's FTP** (`mount_ftp`, what Go > Connect to Server runs) tries `PORT` with the Mac's
  own address first, and falls back to `PASV` in a new session when `PORT` is refused. Behind
  QEMU's user network its `PORT` names 127.0.0.1, which is not the 10.0.2.2 the guest sees, so it
  is refused there (on the laptop's network the two addresses are the same), and it trusts the
  address in a `PASV` reply, the guest's 10.0.2.15, which this Mac cannot reach: `ftpd serve -a
  127.0.0.1` lets it through, and then it mounted SurfOS, listed `/` and `/initrd`, and copied
  `/initrd/README` out byte for byte. Finder opens a session of its own for each transfer.
* **The pager.** The user shell pages every command it runs, so a server that prints a line
  per command or request on its console stops at `--More--` after a screenful and answers no
  client until a key comes: `ftpd serve` showed it, and `httpd serve` had it too (22 requests,
  then nothing). Each line now starts a new screenful first (`ttyctl(TTY_PAGE, 0)`), which
  changes nothing for a program the shell does not page.
* **The first `nc`** ended at the other end's FIN, as if it were the end of the connection. The
  Mac's real `nc -l`, started with its own input at its end (no terminal), half-closes at once:
  SurfOS's `nc` then stopped after 9652 of 300000 bytes. A FIN only says the other end has sent
  all it will; `nc` now ends when both ways have (the typed case aside), and a smoke check sends
  to a listener that half-closes first.
* **QEMU's user network** and the smoke test: a passive port must be forwarded to the same port
  of the guest (EPSV gives a client the port alone), so the harness forwards four ports chosen
  free on the host and starts ftpd with that range (`{ftp_pasv_range}`). Under the harness a
  transfer of a 643 KB file is through before a command sent behind it arrives (this host's and
  QEMU's buffers take it all), so the ABOR and STAT checks use a 2.5 MB file read through a
  4 KB receive buffer, as httpd's slow-client check does.
* **The serial console under Linux** (the first whole run, in Docker): the two checks that make a
  server print a line for each of forty or sixty requests lost most of those lines, and passed on
  this Mac. QEMU writes the serial port to its socket a byte at a time; under Linux each byte costs
  the socket a buffer's overhead, so some hundred bytes fill it while the harness is busy with the
  requests, and QEMU then drops what the guest writes. The checks read the console between the
  requests now (`console_keep()`); nothing was wrong in SurfOS.

## The review (2026-10-25)

An independent review of the whole change, before any commit, found these; each was traced in
the code and fixed, with a check that fails without the fix:

* **TCP:** a connection its program half-closed waits in FIN_WAIT_2 with nothing in flight, and
  nothing bounded that wait (only orphans had a timer there): `nc host port < file` to a Mac that
  then slept would have read for ever. Keepalive probes it now as an open connection
  (`finwait` in `make test-tcp`). A `shutdown()` during a `CONNECT_NOWAIT` handshake returned 0
  and did nothing: it is ENOTCONN now. And the TIME_WAIT check reached its case only when the
  program happened to be slow; a second part reads 1 s late.
* **nc:** `-w` never fired once the other end had half-closed and stopped reading (each pass
  rested instead of timing out), and spun once its time was up. The time is checked at the top
  of each pass now (`ncstuck` in `make test-tcp`: an other end that shuts its window and half-closes;
  a first check through QEMU's user network passed on this Mac and not in Docker, where Linux's
  buffers on this host's side take the whole file and nothing gets stuck).
* **ftpd:** one command held during a transfer stopped the reading of the control connection, so
  an ABOR behind a NOOP waited for the end of the transfer; and STAT during a transfer bypassed
  the 16 KB bound on replies waiting. Four commands are held now, ABOR and STAT still answered at
  once, and nothing more is read while 16 KB of replies wait. A RETR handled before its passive
  connection arrived got its 150, then `accept()` could find no descriptor (425 after the 150):
  the file is opened, and the 150 given, once the data connection is there, as vsftpd and ProFTPD
  do, so a waiting transfer holds its listener alone and three transfers fit whatever their
  clients' order (`@ftpd-descriptors`; a first fix kept a spare descriptor for the connection,
  and the check showed that under QEMU's user network a RETR nearly always comes before its
  connection, which then left room for two). STAT's listing on the control connection gets '?' for a CR or LF in a
  name, which could have forged a reply line. EPRT refuses a digit for its delimiter.
* **FAT (audit R1, older than this work):** `vfs_rename()` refused a folder into itself by
  comparing the paths with their case, and FAT folds it, so RNFR `dir` RNTO `DIR/sub` wrote the
  folder into itself and took it out of its parent. `fat_rename()` follows `..` up from the new
  parent now (`selftest`, `@ftpd-upload`). `mv` had its own check, which ignores case.
* **The harness:** the passive ports were chosen without avoiding the other forwards' ports (a
  rare QEMU start failure); `test_ftp` gained the cases the review listed (a long folder and a
  relative path, EPRT's delimiters, Telnet's sequences inside a line too long, verbs that are not
  ASCII).

## fetch (2026-10-25)

* **On Undertow's transport.** `fetch` links `transport.c`, `url.c`, `config.c`, `util.c` and
  the TLS glue as the browser does, so HTTPS is the browser's: the same roots, the same checks,
  the same messages, no way to skip one. One accessor was added to `transport.c`
  (`ut_transport_eof_clean()`: whether a TLS stream ended with close_notify), nothing else in
  `user/undertow/` changed: Undertow's `http.c` keeps a whole page in memory (1 MiB at most)
  and shows only text, so `fetch` reads its responses itself (`fetchhttp.c`), to the file as
  they come, by the same rules (RFC 9112 read strictly where a looser reading would guess).
* **No file before a 2xx response with something in it** (a 204 or 205 changes no file), and
  none replaced without `-f`. `-c` asks for the rest of a file cut short with a Range request;
  the 206 must start at the file's end and be as long as its range, and one that ends before
  the file does is added with a message (`fetch -c` again). A server that sends all of it again
  (200) leaves the file as it was, as curl and wget refuse it: `-f` downloads it anew. A 416
  whose total is the file's size says it is whole.
* **Over HTTPS, close_notify.** A body that only the end of the connection delimits is whole
  only when TLS's close_notify ended it (RFC 9112 section 9.8); without it fetch keeps what came
  and says it may be cut short. Over HTTP the connection's end is the only end there is.
* **Names.** The last name of the first address's path, percent-decoded, with `_` for what FAT
  cannot hold; never a name the server sends (Content-Disposition) or a redirect's.
* **Redirects** as the browser follows them (301, 302, 303, 307, 308; a loop refused), ten at
  most, never from HTTPS to HTTP: that is a message naming the address, to fetch on purpose.
* **The clock.** Certificates need UTC; `fetch` reads it as the browser does
  (`rtc_offset_minutes` in `undertow.conf`), and `-t` sets it for one run as the browser's
  `clock` does, for a laptop whose clock cannot be trusted.
