# SurfCPU build-out: the parallel tracks (2026-10-15)

The owner's brief is [AGENT-INSTRUCTIONS.md](../AGENT-INSTRUCTIONS.md); read sections 5-10 of
it before you start. Milestone 0 is done in the foundation commit on branch `surfcpu`: the
inventory ([INVENTORY.md](../INVENTORY.md)), the contracts ([MEMORY-MAP.md](../MEMORY-MAP.md)
from [`spec/soc.toml`](../../spec/soc.toml), [SURFBUS.md](../SURFBUS.md), [ISA.md](../ISA.md),
[BOOT-ABI.md](../BOOT-ABI.md), [MODULES.md](../MODULES.md)), the toolchain container and the
command interface. This plan splits the next milestones into tracks that run at the same time,
each in its own git worktree and branch, merged by the integrator into `surfcpu`.

## Rules for every track

1. **Your worktree and branch only.** Work and commit in the worktree you were given, on its
   `sc/<track>` branch. Never push, never merge or rebase other branches, never touch `master`,
   `ai-dev`, `surfcpu`, another worktree, or the main checkout. The integrator merges.
2. **Your paths only.** Change only the paths your track owns (below) plus your own
   `surfcpu/mk/area-<track>.mk`, `surfcpu/docs/evidence/<track>/` and the docs your track
   writes. If you need something outside them, say so in your report.
3. **The contracts are frozen.** Don't edit `spec/soc.toml`, the generated files, SURFBUS.md,
   ISA.md, BOOT-ABI.md, MODULES.md, `firmware/include/surfcpu/bootabi.h`, `rtl/lib/` or
   `rtl/cpu/surfcpu_rvfi.vh`. Build exactly to them. If one is wrong or missing something,
   implement the closest correct thing and describe the proposed change in your report.
4. **Toolchain.** Everything runs in the container: `surfcpu/devenv/run.sh <cmd>` (repository
   mounted at `/work`; `make -C surfcpu <target>` from the Mac does this by itself). Don't
   install anything on the Mac and don't change the Dockerfile; if you need another tool,
   fetch it from a pinned commit or release with a checked SHA-256 into
   `surfcpu/build/third_party/` with a script in your area. No inline `bash -c '...'`
   commands: put multi-step shell work in a script file.
5. **Tests decide.** Every feature has automated tests reachable from `make` and hung on the
   aggregates (`lint`, `test-cpu`, `test-soc`, `test-fw`, `test-os`, `check`). Each commit
   builds and passes your track's tests. Run randomized tests with several seeds. Keep short
   evidence (commands, seeds, counts, pass/fail) in `surfcpu/docs/evidence/<track>/*.txt`.
6. **Honesty.** Simulation, synthesis, programming and physical behaviour are different
   results; report each separately. Nothing here has touched the board: any FPGA or physical
   result is **pending**. Never invent tool output, clock rates, card contents or hardware.
7. **Safety.** Never write a disk device, never program the FPGA or its flash, never format a
   card, never contact a remote build host. Card work uses image files.
8. **Style.** RTL per MODULES.md section 1. C and Python files start with the repository's
   header block (`File: <name> Date: 10/15/26 (SurfCPU)`). Small commits, one topic each,
   messages in the repository's plain style, ending with
   `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
9. **Report.** Finish with a report: what you built (files), the commands that test it and
   their results (numbers), what is pending or known to be missing, proposed contract changes,
   and your commit list (`git log --oneline surfcpu..HEAD`).

## Tracks

### cpu: SurfCPU core (milestone 2)

Owns `surfcpu/rtl/cpu/` (not `surfcpu_rvfi.vh`), `surfcpu/sim/cpu/`, `surfcpu/docs/CPU.md`,
`surfcpu/sim/README.md`.

* `surfcpu_core` exactly as ISA.md: RV32IM + Zicsr + Zifencei, M-mode, the CSR table, traps,
  WFI, FENCE.I, the SurfBus ports and the RVFI outputs.
* The five-stage pipeline IF → ID → EX → MEM → WB with explicit valid/stall/flush per stage,
  forwarding, the load-use interlock, memory backpressure on both ports, precise exceptions and
  wrong-path cancellation. A multicycle core first is allowed as a stepping stone only if it
  helps; the deliverable is the pipeline. Prefer clear, correct logic to speed. A multicycle
  divider is fine.
* The testbench `surfcpu_tb` of MODULES.md section 6 (Verilator, C++ harness, ELF loader,
  random latency and ready stalls, error regions, CLINT-style timer, interrupt and console
  registers, RVFI trace and signature output).
* Directed tests (`sim/cpu/tests/*.S`, self-checking, riscv-tests style) covering brief
  section 10's CPU and pipeline lists: every instruction class, `x0`, immediates, signed and
  unsigned compares and shifts, JAL/JALR link values and bit-0 clearing, misaligned targets,
  load extension and store byte enables, misaligned load/store traps, fetch/load/store access
  faults, every illegal-instruction case of ISA.md, CSR masks and read-only traps, counters,
  ECALL/EBREAK/MRET, all three interrupts with priorities and MIE gating, WFI, FENCE.I with
  self-modifying code, M-extension corner cases (division by zero, overflow, MULH*), RAW
  hazards at every distance, load-use, store-data forwarding, branch flushes and competing
  redirects, and wrong-path stores/MMIO never happening. Run every test with at least three
  latency seeds.
* `docs/CPU.md`: pipeline diagram, hazard and stall rules, trap timing, CSR implementation,
  limits. A Yosys `synth_xilinx` estimate of the core alone (LUTs, FFs, DSPs, BRAM).
* Make targets on `test-cpu` and `lint`. Acceptance: all directed tests pass on several seeds;
  lint clean.

### verif: reference-model checking (milestone 2)

Owns `surfcpu/sim/ref/`, `surfcpu/tools/rv*.py` and `surfcpu/tools/trace*.py`,
`surfcpu/docs/VERIFICATION.md`.

* Spike (in the container, pinned) as the reference: run an ELF with `--log-commits` and
  convert its log to the trace format of MODULES.md section 5 (skip Spike's boot ROM, which runs
  before `0x80000000`).
* A comparator: two traces in, first divergence out (pc, instruction, register write, memory
  access, trap), with context lines; self-tests that inject each kind of mismatch.
* A constrained-random program generator (seeded, Python): RV32IM arithmetic, loads/stores in a
  data area with every width and sign, branches and jumps (forward and bounded loops), CSR
  operations on writable CSRs, deliberate traps (ECALL, EBREAK, illegal instructions, misaligned
  and faulting accesses) with a handler that skips the instruction, dense register dependences.
  Programs end through `tohost` and avoid anything whose timing differs between models
  (interrupts, `mcycle`, `time`).
* riscv-arch-test: choose the suite version that fits Spike and our ISA, pin it, build the
  RV32I/M/Zicsr/Zifencei/privileged tests that apply to an M-mode-only core without PMP, and get
  reference signatures from Spike. Record exactly which tests are in scope and which are not and
  why (a pass is not a certification).
* A runner that takes a DUT command (default: `build/cpu/surfcpu_tb`) and runs all of the
  above against it once it exists. Until the cpu track merges, prove it on Spike against itself
  plus the injected-mismatch tests.
* Optional if time allows: a riscv-formal configuration for `surfcpu_core` (pinned riscv-formal,
  SymbiYosys in the container), ready to run at integration.
* Make targets: `test-ref` (the self-tests, on `test-cpu`) and `test-cpu-ref` (needs the core).

### soc: SurfBus, memories, base peripherals, the SoC and its system simulation (milestones 2-3)

Owns `surfcpu/rtl/soc/`, `surfcpu/rtl/peripherals/surf_{uart,timer,intc,gpio,sysinfo}.v`,
`surfcpu/sim/soc/`, `surfcpu/sim/models/{uart,ddr}_model.*`, `surfcpu/docs/SOC.md`.

* The interconnect of SURFBUS.md section 6: I and D decoders, the error slave, the DDR
  arbiter (data first), the rule that DDR answers with errors before calibration, write
  protection of the ROM, fetch rules.
* Dual-port block RAMs for the boot ROM (initialized from `BOOTROM_INIT` or `+bootrom=`) and
  scratch RAM (byte enables), and `surf_textram` (dual clock).
* `surf_uart`, `surf_timer`, `surf_intc`, `surf_gpio`, `surf_sysinfo` exactly as MEMORY-MAP.md.
* `surfcpu_soc` as MODULES.md section 4. Until the cpu and io tracks merge, use small stand-ins
  under `sim/soc/stubs/` (a scripted bus-master in place of the core; tie-off versions of
  `surf_spi`, `surf_ps2`, `surf_video` with their exact ports) so the SoC builds and lints;
  the stand-ins are never part of a synthesized design.
* Unit tests per block with a SurfBus bus-functional model (random ready stalls, error cases,
  register access rules, FIFO overflow, the 64-bit timer read/write sequences and MTIP, the
  interrupt controller, debounce and button edges, UART loopback at the real divisor and with
  framing errors), and SoC-level tests through the interconnect with the scripted master.
* `sim/models/uart_model` and `sim/models/ddr_model`, and the `surfsim` harness (MODULES.md
  section 7) with the UART and DDR models; the SD, PS/2 and VGA models are wired in at
  integration.
* Make targets on `test-soc` and `lint`.

### io: microSD SPI, PS/2, VGA text (milestone 6 hardware, in simulation)

Owns `surfcpu/rtl/peripherals/surf_{spi,ps2,video}*.v` (and helpers named `surf_video_*`,
`surf_ps2_*`, `surf_spi_*`), the font ROM data and its generator
(`surfcpu/tools/font*.py`, output under `surfcpu/rtl/peripherals/`), `surfcpu/sim/io/`,
`surfcpu/sim/models/{sdcard,ps2_keyboard,vga_capture}_model.*` (and `vga_capture.*`),
`surfcpu/docs/IO.md`.

* `surf_spi` as MEMORY-MAP.md (mode 0, programmable divider, chip select, the waiting DATA read,
  card detect).
* `surf_ps2`: synchronized inputs, falling-edge sampling, start/odd-parity/stop checks,
  recovery from partial frames (the 2 ms timeout), FIFO and overflow, error counters, the
  interrupt; the host-to-device path (inhibit, request-to-send, device-clocked bits, ACK) only
  through the open-drain outputs, never driving a clock continuously.
* `surf_video`: 640x480 timing (800x525; 640/16/96/48 and 480/10/2/33; negative syncs) from
  `pix_clk`, the color-bar test pattern, 80x30 text mode with 8x16 glyphs, palette, cursor
  with blink, hardware scroll, vblank status and interrupt, and every sys↔pix crossing done
  with `rtl/lib` blocks. The font is the repository's code page 437 font (Spleen 8x16 plus
  `driver/fonts/surfos-symbols.bdf`, generated from the same sources as `driver/font8x16.c`;
  keep its licence).
* The three C++ models of MODULES.md section 7 and unit testbenches: SPI against the SD model
  (initialization CMD0/CMD8/ACMD41/CMD58, single and multiple block reads and writes, busy,
  card absent); PS/2 against the keyboard model (typing, extended keys, parity and framing
  errors, partial frames, FIFO overflow, a host command with ACK); video timing measured by the
  capture model, the test pattern, and text decoded back from captured frames.
* Make targets on `test-soc` and `lint`.

### board: the Arty A7 top, constraints, clocks, the milestone 1 design, Vivado scripts

Owns `surfcpu/boards/arty_a7/`, `surfcpu/ip/clocking/` (if needed), `surfcpu/tools/{program.sh,fpga-build.sh,check-wiring.py}`,
`surfcpu/sim/board/`, `surfcpu/docs/{WIRING,BOARD}.md`.

* Fetch Digilent's master XDC files for the Arty A7-35 and A7-100 from a pinned commit of
  github.com/Digilent/digilent-xdc (keep the copies and their SHA-256 under
  `boards/arty_a7/digilent/`, with their licence), and the reference manuals for the Arty A7,
  Pmod VGA, Pmod MicroSD and Pmod PS2. Write WIRING.md: adapter pin → Pmod connector pin → FPGA
  package pin → direction → I/O standard, for the provisional allocation (microSD on JA, VGA on
  JB + JC, PS/2 on JD), with each source cited and every unverified point marked. Note the PS/2
  supply and level-shifting questions for the owner.
* The XDC for our design, generated or checked against Digilent's (`tools/check-wiring.py`:
  every top-level port has exactly one pin, matching WIRING.md and the master XDC).
* Clocking with the vendor's MMCM/PLL primitives: `sys_clk` 25 MHz and `pix_clk` 25.1773 MHz
  (100 MHz x 8.875 / 35.25; check the parameters against the 7-series clocking guide's limits
  for both speed grades), reset synchronization per domain, and simulation models of the
  primitives' behaviour for Verilator/Icarus.
* Milestone 1 design `arty_a7_baseline` (no CPU): LED heartbeat, button and switch echo on the
  LEDs, and a UART banner with the build identity sent every second at 115200 8N1, so the
  owner can see the board, the clock, the reset and the serial link work. A simulation test that
  decodes its UART output.
* `surfcpu_arty_a7_top` for the full SoC (DDR left out behind `HAS_DDR = 0` until the ddr track
  merges), with the PS/2 open-drain IOBUFs and the Pmod pin mapping.
* Vivado non-project TCL (`boards/arty_a7/vivado/`): read sources, XDC, synthesize, optimize,
  place, route, write timing summary, utilization, DRC, clock-interaction and CDC reports, and
  the bitstream, plus the manifest of BUILD-HOST.md. `tools/fpga-build.sh` (reads
  `~/.config/surfcpu/build-host.conf`; `vivado-ssh` and `vivado-docker` flows; a `--dry-run` that
  prints what it would do) and `tools/program.sh` (openFPGALoader: detect, check the IDCODE
  against `BOARD`, refuse a mismatch, `volatile` load; `flash` refuses unless explicitly
  confirmed). These cannot be run for real here: make their logic testable without Vivado or a
  board (dry runs, fake binaries on `PATH`) and mark the real runs pending.
* Resource estimates with Yosys `synth_xilinx` for the baseline and the SoC parts available, and
  a BRAM budget against the 35T and 100T. `docs/BOARD.md`: clock plan, resets, CDC paths and
  their constraints, budgets.
* Make targets on `lint`, `test-soc` (the baseline simulation) and `check`.

### fw: SurfBoot, diagnostics and the card tools (milestones 3-5 software)

Owns `surfcpu/firmware/` (not the generated or contract headers), `surfcpu/tools/{surfimg,mkcard,bin2mem,deploy-sd,isa-audit}.py`,
`surfcpu/docs/FIRMWARE.md`, `surfcpu/docs/CARD.md`.

* `firmware/common/`: start-up (stack, `gp`, `.data` copy, BSS clear), the trap entry and fault
  reporter (prints `mcause`, `mepc`, `mtval` and registers on the UART, blinks an LED code),
  UART and a small printf, timer and sysinfo helpers, the ROM linker script from
  `firmware/ld/surfcpu_soc.ld`. No C library.
* `firmware/diagnostics/`: the milestone 3 BRAM program (build identity, arithmetic and
  M-extension self-checks, scratch RAM tests, timer interrupts ticking, deliberate illegal,
  misaligned and access-fault traps with recovery, UART echo) and a DDR diagnostic packaged as a
  `SURFOS.BIN` (address/data lines, byte lanes, boundaries and aliases, sustained copies, running
  code copied into DDR).
* `firmware/surfboot/`: BOOT-ABI.md end to end: banner, DDR wait with a timeout, SD in SPI mode
  (slow clock first; CMD0, CMD8, ACMD41, CMD58; SDHC/SDXC block addressing and SDSC byte
  addressing; timeouts; card absent), MBR and FAT32 (8.3 names, multi-cluster directories,
  fragmented files, bounded cluster walks, cycle and range checks), the image checks and CRC,
  `BACKUP.BIN` and `CMDLINE.TXT`, the boot info, the handoff, and a UART monitor with useful
  diagnostics whenever booting fails (never a silent hang). Must fit the 64 KiB ROM with room
  to spare; keep the stack and data inside `surfboot_data`.
* Tools: `surfimg.py` (pack and verify, CRC test vectors), `bin2mem.py`, `mkcard.py` (MBR + FAT32
  images with chosen files, optional fragmentation; cross-checked with mtools and fsck.fat),
  `isa-audit.py` (every instruction in a linked ELF is in `rv32im_zicsr_zifencei`; used on every
  firmware and kernel build), and `deploy-sd.py` for the Mac (an explicit mount point; checks
  it is a removable FAT32 volume; installs only project files; keeps user directories; verifies
  every byte; tells the owner to eject; never formats; `--dry-run`; testable against a directory
  stand-in in the container).
* Host tests: the SD/FAT/image code compiled natively and run against generated card images:
  absent card, failed initialization, bad MBR/BPB, exFAT and FAT16 refused, missing file,
  truncated package, bad checksums, out-of-range load or entry, fragmented chains, cycles and
  out-of-range FAT entries, multi-cluster directories, the backup path. Running on the RTL comes
  at integration.
* Make targets: `build-rom` (→ `build/fw/surfboot.{elf,bin,mem}` and the diagnostics), `test-fw`.

### os: SurfOS on riscv32 (milestone 7 software)

Owns `arch/riscv32/`, `include/arch/riscv32/`, `boards/` at the repository root,
`surfcpu/docs/PORTING-RISCV.md`, `surfcpu/mk/area-os.mk`, and the smallest necessary changes to
shared kernel files (each guarded so the x86 build is unchanged).

* `docs/PORTING-RISCV.md`: the portability inventory of brief section 7 (every x86 dependency
  and what replaces it), the machine-mode model and what is absent (no process protection, no
  paging), and the plan.
* A separate riscv32 kernel build (`arch/riscv32/kernel.mk`, reached by `make build-kernel`),
  `-march=rv32im_zicsr_zifencei -mabi=ilp32`, producing `build/riscv32/arty_a7/surfos.elf`,
  `surfos.payload.bin` and `SURFOS.BIN` (packed with `surfcpu/tools/surfimg.py` once the fw track
  merges; a temporary packer is fine meanwhile). The x86 build's files and outputs are untouched.
* `arch/riscv32/`: entry per BOOT-ABI.md (stack, `gp`, BSS, copying the boot info), trap entry
  and exit saving the whole integer context, the RV32 task frame and switching kernel tasks
  through the trap path (pre-emption by the timer with `MRET`), interrupt dispatch, the timer
  tick, interrupt-disable critical sections (no atomics), panic with a backtrace.
* A machine-mode SurfOS with the kernel shell and at least two scheduled kernel tasks; keep the
  SurfOS identity and as many commands as are portable; leave out PC hardware (PCI, ATA, USB,
  ACPI, Wi-Fi, x86 paging, ring-3 processes) and say so.
* Two boards: `boards/qemu_virt/` (a separate HAL for QEMU's `virt` machine, for automated tests
  now: its UART, CLINT timer, and a RAM disk image) and `boards/arty_a7/` (our UART, timer,
  intc, GPIO, the SD card over our SPI as a block device, the PS/2 keyboard translating scan code
  set 2 for the existing keyboard code, and a console on our 80x30 text display), written to
  MEMORY-MAP.md and host-tested where possible.
* FAT on the card: the existing VFS, block cache and `fs/fat.c` over the SD block device
  (read-only first, read-write once tested), flush and unmount.
* Tests: `make test-os` boots the qemu_virt kernel in QEMU (container) and drives the shell over
  the serial console: banner, help, tasks running and sleeping, timer, FAT read and write on the
  RAM disk. And the x86 kernel must stay green: build it and run `make test-all`, `make unittest`
  and `make test-usb` at O0 and O2 through `devenv/` with your own Docker volume
  (`SURFOS_VOLUME=surfos-sc-os`) before committing changes to shared files.

### ddr: DDR3L integration (milestone 4 groundwork)

Owns `surfcpu/rtl/soc/ddr/`, `surfcpu/ip/mig/`, `surfcpu/ip/litedram/`, `surfcpu/sim/ddr/`,
`surfcpu/docs/DDR.md`.

* `surf_ddr_bridge`: the SurfBus slave of MODULES.md in the sys domain, crossing to the memory
  controller's clock domain, 32-bit to the controller's data width with byte masks, calibration
  status synchronized back, and a watchdog that answers a stuck access with an error.
* AMD MIG 7-series for the Arty's DDR3L: the MIG project file and a TCL generation recipe
  (from Digilent's board files for the Arty A7, pinned and cited), the controller's clocking
  needs, and how it fits the board top. It cannot be generated here: mark it pending a Vivado
  host.
* The open alternative for the open-source flow: a LiteDRAM configuration for the Arty and a
  pinned generation script; generate it in the container if you can and record what comes out.
* A behavioural model of the controller interface (calibration delay, random latency,
  back-pressure, read-data ordering) and bridge tests: every byte lane, boundaries, aliases,
  random traffic against a reference memory, errors before calibration, the watchdog.
* Make targets on `test-soc` and `lint`.

## Integration (the integrator, after the tracks report)

Merge order into `surfcpu`, running `make check` after each: soc, cpu, io, fw, verif, board,
ddr, os, flow. Then: the real core inside the SoC, the SD/PS/2/VGA models in `surfsim`,
SurfBoot booting a kernel package from a card image in simulation, the verification runner
against the core, an independent review of each risky track, and fix rounds. Then the
owner-facing guides and the hardware steps, which need the owner, the board and a build host.
