# SurfGPU's next milestones: the SurfOS driver (G3) and triangles with depth (G4) (2026-10-25)

The owner asked (2026-10-25) to build out more of the SurfGPU: "take part of the processor and
create a GPU for it". The GPU of [GPU.md](../GPU.md) already takes its part of the chip: VRAM in
76 of the 100T's block RAMs, the graphics scan-out in surf_video and the 2D drawing engine
surf_gpu (G0 to G2, done in simulation and synthesis, six reviews fixed, not yet run on a
board). Two things are missing before it is a GPU the system can use: SurfOS cannot drive it
(G3), and it can draw nothing but 2D (G4). GPU.md section 11 planned both; this brief fixes
their architecture (the integrator's decisions) and splits them into two tracks that run at the
same time:

| Track | Branch, worktree | Milestone |
|---|---|---|
| gpu-g3 | `sc/gpu-g3`, `06-restoration-gpu-g3` | the SurfOS driver, the `gfx` command, a 2D demo |
| gpu-g4 | `sc/gpu-g4`, `06-restoration-gpu-g4` | TRIANGLE (flat and Gouraud), a 16-bit z-buffer, FLIP at vertical blanking, a spinning cube |

Both start from `sc/gpu-integ` (sc/gpu 5551bce with surfcpu a2958c7 merged: the current kernel).
The integrator merges each into `sc/gpu-integ` after its checks and an independent review; a
third round then puts the cube into SurfOS (`gfx cube`, below). sc/gpu-integ merges into surfcpu
only after the board tests, as G0 to G2 were to.

## Rules for both tracks

The rules of [2026-10-15-tracks.md](2026-10-15-tracks.md) ("Rules for every track", 1 to 9)
apply, with these changes and additions:

1. **Paths.** gpu-g3 owns `boards/arty_a7/` (new files for the GPU, and the board's command table
   and driver list), `arch/riscv32/` where the driver needs it, `surfcpu/mk/area-gpuos.mk` (new),
   `surfcpu/docs/evidence/gpu-g3/`, GPU.md section 15 (new) and GPU.md 11's G3 row. gpu-g4 owns
   `surfcpu/rtl/peripherals/surf_gpu*.v`, the GPU's lines of `surf_video.v` and `surfcpu_soc.v`,
   `surfcpu/sim/gpu/`, `surfcpu/sim/models/gpu_model.*`, `surfcpu/firmware/include/surfcpu/gpu.h`,
   `surfcpu/firmware/diagnostics/gpu*`, `surfcpu/mk/area-gpu.mk`, `surfcpu/docs/evidence/gpu-g4/`,
   GPU.md section 16 (new), section 14 (the physical tests) and 11's G4 row. Neither edits
   PROGRESS.md or the other's paths; the integrator does PROGRESS.md at each merge.
2. **The contracts.** gpu-g4 changes the GPU's contract: `spec/soc.toml` (bump `soc_version` to
   0.4.0; regenerate with `make gen`; every user updated in the same change, as surfcpu/CLAUDE.md
   says) and gpu.h. The G2 commands keep their encodings and behaviour exactly, so a GPU1 program
   runs unchanged. gpu-g3 changes no contract.
3. **The x86 kernel is untouched.** Neither track changes a shared kernel file (kernel/, fs/,
   driver/, mm/, lib/, shell/, include/ outside include/arch/riscv32/). If the driver really needs
   one, stop and say so in your report instead: a shared file means the x86 suites again.
4. **Model first.** Every new behaviour is in the C model (sim/models/gpu_model.c) before the RTL,
   and the RTL is compared with the model, bit for bit, at every FENCE. GPU.md states the
   arithmetic exactly, so that the model, the RTL and a reader all get the same pixels.
5. **Board and flash.** The physical tests are the integrator's, with the owner. Never program the
   FPGA or the flash; never contact the board. Build bitstreams (gpu-g4) only as files.
6. **Resources.** Block RAM is the scarce part: 112.5 of 135 RAMB36 are used in the GPU designs.
   G4 adds no block RAM (the z-buffer is in VRAM). LUTs (about 82 % free) and DSP48E1 (236 free;
   multipliers only: the flow keeps `xilinx_dsp.multonly`, OPEN-FLOW.md 6.1) may be spent.
   sys_clk stays 25 MHz and must keep the flow's slack rule (max(0.5 ns, 4 %)).
7. **make check** passes on every commit you hand back (it takes about 30 minutes; run it before
   the hand-back, not after every commit). Keep what you add to it under about 4 minutes.
8. **Report.** As rule 9 of the old brief, with the numbers, plus the GPU.md sections written.

## G3: the SurfOS driver (track gpu-g3)

SurfOS on the Arty (boards/arty_a7) has a text console and no graphics. G3 makes the GPU a
kernel driver with a shell command, so that the owner can draw from the SurfOS shell on the
board, and the kernel's later graphics (the cube, a desktop) have a driver to stand on.

**The driver** (`boards/arty_a7/gpu.c`, `gpu.h`):

* Present when sysinfo.FEATURES.GPU is set and gpu.ID reads "GPU1" (0x31555047) or "GPU2"
  (0x32555047, G4's command set, which adds commands only). Anything else: no GPU, said once at
  boot (`+GPU:` lines, as `+USB:` and `+PART:` on x86) and by `gfx`. It is a driver in
  board.c's list, so `drivers` shows it.
* Command words go to CMD only while FIFO_FREE says there is room: read FIFO_FREE, write that many
  words, read it again. A wait for room is bounded (two seconds without a word taken is a stopped
  engine: ABORT, say so, fail). Commands of two consoles never interleave: the driver is claimed
  for one command's run at a time (a mutex; kernel/console.c rules on kernel commands in the root
  CLAUDE.md apply: print on `curTask->con`, no statics two consoles could use at once).
* Fences: each submission that must be finished ends with a FENCE whose value the driver counts;
  waiting for it uses the GPU interrupt (intc source 5, IE.FENCE) where the board's interrupt
  path allows, else a poll with sleeps; either way bounded.
* Errors: after a command, STATUS's sticky bits (OVERFLOW, BAD_OPCODE, BAD_PARAM) are read; any one
  is said in words, cleared, and the engine ABORTed back to a known state (target and clip set
  again).
* Display modes: video CTRL.MODE 1 (text), 2 (graphics), 3 (graphics with the text over it). The
  text console's driver (textcon.c) keeps a copy of CTRL and rewrites it for the cursor, so a
  mode change goes through textcon (a function there that sets the mode bits of its copy under
  the console lock), never around it. GFX_BASE, GFX_STRIDE and GFX_SCALE follow GPU.md section 3's
  frame latch rule (written between VBLANK_EV and 1.3 ms after it, to change one frame
  together). In mode 3 the console's text, whose background colour 0 is transparent, floats over
  the picture: the shell stays usable while a picture shows.
* The palette (GPAL): left as configuration made it (RGB332) unless a command loads another;
  the driver can load named palettes (RGB332, grey ramp, 8 shaded ramps of 32 for G4's Gouraud).
* Text into VRAM with EXPAND, from the kernel's own 8x16 code page 437 font (driver/font8x16.c,
  compiled from where it is, unchanged), so `gfx text` matches the console's glyphs.

**The command** `gfx` (board_commands in board.c, the code in `boards/arty_a7/gfx.c`):

```
gfx                          the GPU: ID, VRAM, mode, base/stride/scale, FIFO, fences, errors, frames
gfx mode text|gfx|overlay [1|2]   the display mode and scale (1 = 640x480, 2 = 320x240 doubled)
gfx clear [c]                the target filled with colour c (default 0)
gfx fill x y w h c           FILL_RECT
gfx rect x y w h c           an outline (four LINEs)
gfx line x0 y0 x1 y1 c       LINE
gfx copy sx sy dx dy w h [key]   COPY_RECT, with a transparent colour
gfx text x y fg bg|- words...    EXPAND with the console font (- : transparent)
gfx pal rgb332|grey|ramps|<n> <rgb444>   load a palette, or set one entry
gfx put x y c / gfx get x y  one pixel through the CPU's VRAM window (0x3000_0000)
gfx crc                      FRAME_COUNT and FRAME_CRC of a frame begun after the last change
gfx bench                    fills, copies, lines and text: pixels per second
gfx demo [seconds]           an animation at 320x240, double-buffered with page flips: moving
                             filled rectangles, lines, copies, text; prints frames per second;
                             Ctrl+C ends it and puts the display back as it was
gfx reset                    ABORT, sticky bits cleared, target and clip back to the reset ones
```

Coordinates and sizes as GPU.md section 5 gives them (signed x, y; the clip cuts, nothing wraps).
Every command returns CMD_OK, CMD_FAIL or CMD_USAGE, checks its arguments, and returns rather than
loops when its input ends; the demo and bench end on Ctrl+C (the task's interrupt flag) with the
GPU idle and the display mode as before.

**Tests:**

* A host test of the driver (boards/arty_a7/tests/, as test_sd.c and test_keyboard.c are): the
  driver's code built for the host against a register stand-in that feeds CMD words into
  sim/models/gpu_model.c and answers STATUS, FIFO_FREE and FENCE as the engine does; each `gfx`
  drawing command's VRAM afterwards equal to the model's picture of the same scene; the FIFO-room
  rule (a FIFO that stays full, a stopped engine), errors cleared and said, two claimants.
* SurfOS on the RTL SoC with the GPU (build/sim/surfsim_gpu, HAS_GPU = 1, HAS_DDR = 1), booted
  from a card image as test-gpu-system-boot does: `gfx`, a sequence of drawing commands, `gfx crc`
  equal to the CRC the C model computes for the same picture, and equal to the CRC of the frame
  surfsim captured at the VGA pins (`--vga-dir`); `gfx mode overlay` with the console's text over
  the picture; `gfx demo 1` running and ending. One boot, on `make check` (`test-gpuos`, in
  `mk/area-gpuos.mk`), at most about 3 minutes.
* QEMU virt (boards/qemu_virt/test_os.py): `gfx` says there is no GPU; nothing else changes. The
  Arty build without a GPU (surfsim, HAS_GPU = 0) likewise.

**Physical (the integrator's, with the owner):** the DDR+GPU bitstream over JTAG, SurfOS from the
card with this kernel, `gfx demo` on the monitor, `gfx crc` equal to the model's.

## G4: triangles, depth and flips (track gpu-g4)

GPU.md section 11's G4: triangles (flat, then Gouraud in the palette), the 320x240 double-buffered
mode with page flips at vertical blanking, a z-buffer in VRAM, and a spinning cube at 30 or more
frames a second without tearing. The command set becomes "GPU2"; everything of GPU1 stays.

**The integrator's decisions** (refine them in GPU.md section 16; say where and why you deviate):

* **gpu.ID = 0x32555047 ("GPU2")**, soc_version 0.4.0. New opcodes from 0x0A; the G2 opcodes and
  their header bits unchanged. The parameter counter of the sequencer grows (TRIANGLE has 6).
* **SET_ZBUF** base; stride: the depth buffer, 16 bits a pixel (pixel (x, y) of the target has its
  depth at base + y * stride + 2x, little-endian). Refused (BAD_PARAM, nothing changes) unless
  base and stride are multiples of 4 and the target's W x H fits in VRAM at that base and stride
  without two lines sharing a word, as SET_TARGET is. A reset leaves no depth buffer; a TRIANGLE
  that tests or writes depth without one is refused.
* **TRIANGLE**: header bits 7:0 the flat colour; GOURAUD (interpolate the vertices' colours);
  ZTEST (draw a pixel only where its depth passes against the buffer); ZFUNC (0 = less, 1 = less
  or equal); ZWRITE (write the depth of every pixel drawn); CULL_CW and CULL_CCW (draw nothing
  when the triangle's winding on the screen is that one). Six parameter words: for each vertex,
  `X | Y << 16` in signed 12.4 fixed point (pixels and sixteenths, -2048 to 2047.9375), then
  `Z | C << 16` (16-bit depth, 0 near and 0xFFFF far; colour index in bits 23:16).
  * Coverage: pixel (px, py) is drawn when its centre (px + 1/2, py + 1/2) is inside the
    triangle, with the **top-left rule** for centres exactly on an edge, computed with exact
    integer edge functions on the 12.4 coordinates. So triangles that share an edge draw each of
    its pixels exactly once: no gaps, no double draws. A zero-area triangle draws nothing.
  * Depth and colour: affine (screen-space) interpolation of the vertex values through plane
    gradients made once per triangle (setup: one division per gradient, a sequential divider; no
    division per pixel), in fixed point with at least 16 fractional bits, each pixel's value
    computed from the triangle's start value and the gradients so that no rounding accumulates
    along a row; the result clamped to the smallest and largest of the three vertex values (a
    Gouraud colour then never leaves its palette ramp). GPU.md section 16 gives the arithmetic to
    the bit.
  * The walk: the bounding box cut by the clip (the effective clip of section 5), row by row, in
    groups of four pixels, the target's words, as FILL_RECT walks: the four lanes' edge functions
    at once; a group with no lane inside costs one cycle and no access; a covered group without
    depth is one write with byte enables; with depth, its two depth words read, the lanes
    compared, then the depth words (ZWRITE) and the colour word written with byte enables. Aim at
    about 6 cycles for a covered group with depth and 1 without, plus a setup of a few hundred
    cycles.
  * Clipping is the clip rectangle's (a scissor): vertices may lie anywhere in the 12.4 range;
    nothing outside the effective clip is written, nothing wraps.
* **FLIP** base: waits for the next vertical blanking (as WAIT_VBLANK), then writes base into video
  GFX_BASE as a CPU store would (a port from surf_gpu into surf_video's register, in sys_clk), so
  the next frame shows it (the frame latch at line 524 comes after). Commands after FLIP run once
  it is written and may draw into the picture shown until then: its last line has been sent. With
  a back buffer drawn, then FLIP, a picture never tears and the CPU never times anything.
* **Clearing depth** needs no command: FILL_RECT 0xFF over the depth buffer's bytes (a target set to
  it) makes every depth 0xFFFF. GPU.md says so with the exact command words.
* **The 320x240 double-buffered layout** (GPU.md section 2 left room for it): picture A at 0,
  picture B at 76,800, depth at 153,600 (stride 640), 307,200 bytes in all: VRAM exactly.
  GFX_SCALE 2 shows either picture doubled to 640x480.

**Tests:** what the G2 tests did for the 2D commands, for each new one:

* The model against hand-worked cases (tiny triangles pixel by pixel, the top-left rule at each
  kind of edge, both windings, culling, clamping, depth functions, FLIP's timing) and properties:
  a square split into two triangles, a fan around a point and random triangulated meshes cover
  every pixel of their hull exactly once (a counting mode of the model, not of the RTL).
* The RTL against the model: directed tests of every flag and edge case, then random command
  streams (random triangles, off-screen, huge, tiny, degenerate, mixed with the 2D commands, with
  the CPU on port A) with VRAM compared byte for byte at each FENCE, several seeds; ABORT inside a
  TRIANGLE; FLIP against the frame latch. Mutants for each rule (the tie rule, a lane, the depth
  function, the cull sense, the clamp, the gradient rounding, FLIP before blanking) caught.
* gpudiag: GPU2's checks and scenes (flat and Gouraud triangles, a shared-edge mesh, two
  intersecting triangles with depth, a FLIP) with their FRAME_CRCs from the model, the check
  totals updated (and gpudiag_check.py), on the RTL SoC and on the synthesized netlist
  (gpu-netlist-sim, once, near the end).
* **The cube.** After its checks, gpudiag (the same bitstream, so the owner loads one) runs a
  spinning cube: the CPU turns eight vertices in fixed point, the engine draws twelve Gouraud
  triangles with depth into the back buffer at 320x240, then FLIP. Every frame's picture is
  deterministic, so the build computes each frame's expected FRAME_CRC with the model (as the
  scenes' are), and gpudiag prints once a second the frames drawn and shown and whether every
  frame shown was a whole drawn frame (each FRAME_COUNT's CRC one of the expected ones): the
  tearing check on the board without a camera. In simulation, a few frames of it with their CRCs.

**Synthesis:** gpudiag and ddr_gpu through the open flow with every gate (LVS, the netlist check,
the clock checks, the slack rule), recorded as section 12.2 records G2: LUTs, flip-flops, DSP48E1,
block RAM, each clock's slack, the critical paths, dram_clk's margin in ddr_gpu. One nextpnr run at
a time on this Mac.

**Physical (the integrator's, with the owner):** gpudiag over JTAG: its UART transcript PASS with
the expected CRCs, the scenes and the cube on the monitor, the cube's frame rate (30 or more) and
no torn frame; then ddr_gpu boots SurfOS as before.
