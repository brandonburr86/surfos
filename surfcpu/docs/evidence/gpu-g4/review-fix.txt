SurfGPU G4: the review of 3fea963, its fixes and the bug-back runs (2026-10-26). GPU.md 16.12 is the record;
this file has the runs. In the surfcpu-toolchain container (Verilator 5.032, gcc), times UTC as it printed them.
The fixes are cd523de to db3e65c (no RTL or model change). The runs below were made on db3e65c's sources (some
just before they were committed, as said), with GPU.md and this file not yet committed: the builds say dirty.

How the bug-back runs were made (scratch scripts under the worktree's build/g4-fix/tools, not committed):
- engine: test_gpu built by Verilator exactly as sim/gpu/mutants.py builds it (the mutated copy of the RTL file,
  the other files as they are), from a given test source: db3e65c's sim/gpu/test_gpu.cpp, 3fea963's, or db3e65c's
  with 3fea963's random_vertices() put back; each seed run with --chunks 120 (and --random-only where said); per
  run, the verdict, the FENCEs whose VRAM differed from the model, the first failing check's label.
- SoC: surfsim with HAS_GPU = 1 built from the mutated copy as mutants.py's soc_one builds it, then each boot ROM run
  to its first GPUDIAG line (at most 700 million cycles) and judged as soc_one judges (gpudiag, gpudiag_check in its
  board and simulation forms). Three ROMs: gpudiag as at bfaac48 (3fea963 with bfaac48's gpuscenes.c: the only
  firmware difference between the two), as at 3fea963 (both from git archives, build id 3fea963) and as fixed.
- each rule of gpudiag_check taken out of a copy of it, test_gpudiag_check run against the copy;
- the old rate rule put back into a copy of db3e65c's gpudiag.c, its gpudiag-slow.mem run on the RTL SoC.
