== Why: the memory cap
  The integrator read the Docker VM's kernel log with
  docker run --rm --cap-add SYSLOG surfcpu-toolchain:2026-10-15 dmesg. As they quoted it:
  | Memory cgroup out of memory: Killed process ... (python3) total-vm:2629136kB, anon-rss:2581292kB
  There were 25 such kills still in the buffer. The cgroup's task list at one kill: lvs_equiv 236,425 anon
  pages (about 0.95 GB) and python3 645,307 (about 2.6 GB). The cgroup's anon memory was 3,612,012,544
  bytes against its limit of 3,584,000 kB, and its file pages only 48 MB.
  So on the largest questions the z3cmd process, with lvs_equiv's 0.95 GB beside it, went past the cap by
  tens of MB and was killed. Its question got no answer, and lvs_equiv counted the point unknown. G4's run
  of the same questions (20971 proved, 0 differ, 0 unknown in 13 h 52 min; OPEN-FLOW.md 6.9) fitted.

== What it shows
  The z3cmd route works on this design: 20,898 points proved, none differing, in 14 h 50 min within the
  86,400 s limit, each solver process given back when its question was answered. Only memory left the
  73 open, and the route keeps each question's memory its own. Whether one run may have more than the
  3.5 GB cap is the integrator's question to the x86 lead, and it waits for the answer.
  Since this run, lvs_prove counts the questions the solver never answered
  (tools/openxc7-steps.sh lvs_unanswered). Run on copies of this run's check-lvs.txt and
  lvs/questions.log, under /bin/sh and dash, it gives:
  | BLOCKED (73 unknown, none differ; 73 got no answer from the solver: killed?)
  | z3cmd: 73 of the 20971 questions lvs_equiv asked got no answer from the solver: they have no line in
  |   lvs/questions.log, so its process ended before Z3 answered (killed? the memory cap's out-of-memory
  |   killer, if dmesg says so), and lvs_equiv counted them unknown
  The first line is the LVS result. The second is appended to check-lvs.txt.
