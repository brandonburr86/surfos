1. First run: z3, slaves answering with an unconstrained error flag.
   insn_add_ch0 PASS (9 min); insn_lw_ch0 FAIL in step 20 (9 min): the assertions of
   rvfi_insn_check.sv on pc_wdata (line 178), mem_addr (181), the read lanes (193) and trap (198),
   i.e. a load that trapped where the specification expects none.
   Cause, reproduced later with bmc3 in 12 s and read from the counterexample (assertions on
   rd_addr, pc_wdata and the read lanes): the slave answered a load (lw x1, 0(x0) at pc 0x18) with
   rsp_err = 1; the core took the load access fault (trap = 1, no rd, no memory access, pc_wdata =
   mtvec = 0), as ISA.md requires, while riscv-formal, with every address valid, expected the load to
   complete. A fault of the slave model, not of the core.

2. The fix (this commit): the slaves raise rsp_err exactly for addresses from 0xF0000000 up, which
   checks.cfg declares invalid (RISCV_FORMAL_VALIDADDR), so the checks expect an access fault there
   and no fault elsewhere. riscv-formal cannot accept a bus error at an arbitrary address without
   rvfi_mem_fault signals, which surfcpu_rvfi.vh does not have.
   Mutation check of the fix (the generated copy of the slave changed back to random errors, the
   address rule kept): insn_lw_ch0 and insn_sw_ch0 FAIL in about 1 s (an invalid address answered
   without error, so the core completed what the check expects to fault): the checks see bus errors.

3. z3 with the fix, 12 checks, 4 jobs, 55-minute limit: none finished (insn_lw, insn_sw, insn_lbu,
   insn_sh spent 52 minutes in the step-20 assertion query; the other 8 never started).

(cycles after reset) for any bus timing the slaves allow, any read data and any interrupt input;

mutation in 2); for the other checks no vacuity test was run.
