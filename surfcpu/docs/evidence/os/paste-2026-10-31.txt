A paste at the UART on the RTL SoC, 10/31/26, after the merge of the two lines (ai-dev 026aab7). GPU.md 15.9's
addendum run again, and its proposed fix tried. The tick, the cube and the shell are the kernel's; the times are
surfsim's simulated ones.

The run (surfsim_gpu, the boot card, CMDLINE "ascii", 700 million cycles at most):
  --send 'PROMPT=gfx cube 2\r'
  --send 'cube 1 s: [^\n]*\n=' followed by N bytes at the line's 115200 baud (87 us each)
  then either --send 'PROMPT=echo after the burst\r', the next command the moment the prompt shows,
  or --ps2-send on the prompt typing `irqstat`, then --send on its end: `echo uart works\r` (is the line alive?)

The kernels:
  old     ai-dev as it stood: wake_up() and poll_wake() for each byte dropped, the guard switches a source off
  tty     old + kernel/tty.c's drop without the wake-ups (surfcpu/docs/GPU.md 15.9's proposed fix)
  both    tty + arch/riscv32/irq.c's rest until the next tick (B88, B89)

kernel  paste              cube's second second            the serial line afterwards
old     3,000 x DEL        44 drawn, 16 missed             the next command lost
tty     3,000 x DEL        54 drawn,  3 missed             "+IRQ: source 0 stays pending ...: switched off": dead
both    3,000 x DEL        48 drawn,  4 missed             the next command lost, but see below
old     10,000 x DEL        9 drawn, 50 missed             "+IRQ: source 0 stays pending ...: switched off": dead
both    10,000 x DEL       12 drawn, 40 missed             irqstat typed, `echo uart works` at the UART: runs
                                                           (IRQ 0 2517 times, rested until a tick 78 times)
both    3,000 x 'x'        49 drawn,  4 missed             255 x echoed, then not one byte of the next command

So:
1. The guard was wrong before the fix was tried. It took a source pending after 32 rounds for a handler that does
   not clear it. A UART at the line's speed is pending again each round: 32 rounds of serial_isr()'s 256 bytes is
   8 KB. With the drop made cheaper than the line, serial_isr() empties the FIFO and a round takes about 4 bytes
   (10,000 bytes in 2517 rounds), so with the fix alone 3,000 bytes tripped it. Fixing kernel/tty.c alone would
   have left SurfCPU worse off. No x86 test can see this: the guard is riscv32's.
2. The wake-ups were a real cost: 16 frames missed to 4 for 3,000 bytes. A dropped byte still costs SurfCPU most of
   the line's 87 us, so a longer paste still takes most of the CPU (40 missed for 10,000 bytes), and the tick comes.
3. The lost command was never the receive path's doing. The paste ended 0.7 s before the prompt, so nothing was
   receiving then. The queue holds the paste's first 255 bytes and the command takes 1.9 ms to arrive, before the
   shell has read a key: with printable bytes all 255 come back and no byte of the command. The board note stands:
   after a long paste, wait a moment, or type it.
