SurfOS os track: the x86 kernel and the shared files the riscv32 port changes
Round 5 (10/16/26, sc/os-5: the physical test kit) changes no shared file, only files under surfcpu/ (its tools,
surfsim's test harness, make files, docs), so the x86 suites were not run again for it.
Seven rounds with x86 runs, newest first. Round fs-fix-3 (10/16/26) changes the x86 kernel on purpose: a review of B12-B19
and its fixes (audit B20-B26: a rename sets the replaced file's refused blocks aside only for its second order point;
every failed block looked at, chain walks bounded; a refused straight write drops the clean cached copies; a gap of zeros
all or nothing; an undo that cannot be done makes the volume read-only; a write's cut-back frees its clusters once the
cut is on the disk; each sync its own count, and blocks set aside are other tasks' syncs' debt).
Round fs-fix-2 (10/16/26) changes the x86 kernel on purpose: a review of B5-B11 and its
fixes (audit B12-B19: a block waits only for the older changes it may point at, and a sync owes what was dirty when it
began; failed runs retried in every sync; a refusing device asked again; a refused straight write changes nothing; a
refusing file's blocks set aside when it is removed; rename and create that fail change nothing; a sync gives up on a
hold after 10 s). Round fs-fix (10/16/26) changes the x86 kernel on purpose: the review of B1-B4 and its fixes
(audit B5-B11: the block cache's write order, a refusing device's share of the cache, failed order points put back,
close and umount report what was not written). Round 4 (10/16/26) changes the x86 kernel on purpose: a FAT write that
stops early gives its clusters back (audit B4), and cp says why a write came up short.
Round 3 (10/16/26) changes the x86 kernel on purpose: the block cache keeps a failed
write and writes in order, FAT gives its blocks that order, eject keeps a disk it could not write (audit B1-B3).
